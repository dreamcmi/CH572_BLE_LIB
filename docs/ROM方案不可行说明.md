# 为什么 ROM 方式在 CH572 上跑不起来 —— 根因分析与结论

> **结论先说**：CH572 只有 12 KB RAM，而 ROM 方案要求协议栈的 `.highcode` 段
> （10,496 字节）必须完整驻留在 RAM，加上协议栈的 `.data`/`.bss` 共占 11,700 字节
> —— **应用只剩下约 600 字节，放不下任何东西**。
>
> **因此 ROM 方式（`CH572BLE_ROM.hex`）在 CH572 上不可行，请使用静态库方式。**
> API 与调用方式两种模式完全一致，应用源码不用改。

---

## 一、实机现象

烧录 `CH572BLE_ROM.hex` + 应用固件后，串口输出卡在：

```
[3/6] 正在初始化 BLE 协议栈（CH57x_BLEInit）...
  [BLEInit 1/9] 配置 SysTick
  [BLEInit 2/9] 配置 MISC_CTRL 射频位
  [BLEInit 3/9] 登记 LLE 中断入口
  [BLEInit 4/9] 设置 BLE 中断优先级
  [BLEInit 5/9] 清零 bleConfig_t
  [BLEInit 6/9] 填内存堆参数
  ← 卡死在这里，没有 [BLEInit 7a/9]
```

时基、时钟、版本校验、前 6 步初始化全部正常 —— 说明协议栈本身没问题，
问题出在第 7 步 **读 MAC 地址**。

## 二、定位过程

### 第 1 步：反汇编确认卡在哪条指令

```
1b98:  jal iprintf            ← 打印 [BLEInit 6/9]
1ba6:  jal FLASH_EEPROM_CMD   ← 卡在这里（= GetMACAddress）
1bcc:  jal iprintf            ← [BLEInit 7a/9]，从没执行到
```

### 第 2 步：看 FLASH_EEPROM_CMD 内部跳去哪

```asm
1e88:  li    a5,6
1e8a:  bne   a4,a5,1e98
1e8e:  auipc ra,0x1ffff
1e92:  jalr  -1948(ra)     # -> 0x200006f2  ★RAM 地址★
```

`cmd = 6 (CMD_GET_ROM_INFO)` 时，它跳转到 **`0x200006f2`** —— 这是一个
**RAM 地址**，而不是 Flash 里那个函数的实际位置。

### 第 3 步：确认这些函数"应该"在哪

对比两种构建方式里 `FLASH_CMD_*` 的地址：

| 构建方式 | `FLASH_CMD_ROM_WRITE` 地址 | 判断 |
|---|---|---|
| **静态库方式** | `0x20000de6`（**RAM**） | ✓ 正确 |
| **ROM 方式** | `0x33ed0`（**Flash**） | ✗ 错位 |

静态库方式的链接脚本把 `.highcode` 段正确放在 RAM（VMA `0x20000000`），
函数真的在 RAM 里，所以 `jalr 0x2000xxxx` 能跳对。

我的 ROM 链接脚本为了"省 RAM"，把 `.highcode` 留在 Flash 做 XIP ——
于是 RAM 的 `0x2000xxxx` 区域是**空白的**，跳进去就是一片 `0x00000000`
指令（或垃圾），程序卡死。

### 第 4 步：为什么这些函数必须放 RAM

ISP572 的 Flash 操作函数被编在 `.highcode` 段，运行期地址固定 `0x20000000` 起。
这是**硬性要求**，不是优化：

> **擦写 Flash 时，CPU 不能从 Flash 取指。**
> 所以执行擦写的那段代码必须位于 RAM。

WCH 的静态库就是这么编的（这些函数的运行期地址写死在 `0x2000xxxx`），
`FLASH_EEPROM_CMD` 内部用绝对地址调用它们。

## 三、为什么不能在 ROM 方式下也放 RAM —— RAM 不够

把 `.highcode` 正确放进 RAM 后实测：

| 项目 | 大小 | 说明 |
|---|---|---|
| ROM 镜像 `.highcode` | **10,496 字节** | 必须完整驻留 RAM |
| ROM 镜像 `.data` | 68 字节 | |
| ROM 镜像 `.bss` | 1,136 字节 | |
| **ROM 镜像合计** | **11,700 字节（11.43 KB）** | |
| CH572 RAM 总量 | 12,288 字节（12 KB） | |
| **剩余给应用** | **588 字节** | ✗ 放不下任何应用 |

而应用自己还需要 `.data`（584）+ `.bss`（5,308）= 5,892 字节。
两者相加 **17,592 字节**，超出 RAM 总量 **5,304 字节**。

### 为什么 ROM 的 `.highcode` 要 10.5 KB，而静态库只要 4 KB？

因为 **ROM 链接必须关闭 `--gc-sections`**：

- 跳转表需要**每一个** API 都有确定地址，包括当前没人调用的
- 开 `--gc-sections` 会把"没人调用"的函数裁掉，跳转表项就指向空地址
- 关掉 `--gc-sections` 后，`.highcode` 段里会保留**全部**带该段属性的函数

实测对比：

| | `.highcode` 大小 |
|---|---|
| 静态库方式（开 gc） | 4,044 字节 |
| ROM 方式（关 gc） | **10,496 字节** |

### 能不能只把 ISP 那部分搬进 RAM？

不行。原因：**`libISP572.a` 里只有一个整体对象 `ISP572.o`**

- 链接其中任何一个函数，整个对象都会被拉进来
- 它的 `FLASH_CMD_*` 地址是写死的（`0x20000de6`、`0x20001072`…），
  分布在 `0x20001072 - 0x20001335` 区间
- 要从 `0x20000000` 连续填充才能对齐到这些固定地址
  → 又回到"需要 10.5 KB"的结论

## 四、结论与建议

### ROM 方式在 CH572 上不可行

12 KB RAM 装不下"ROM 镜像 11.7 KB + 应用 5.9 KB"。这是**硬件资源约束**，
不是代码写法问题，无法通过调参绕开。

> 对比：CH592 有 26 KB RAM、448 KB Flash，RAM 是 CH572 的两倍多，
> 所以 CH59x 能做 ROM 方式。CH572 做不了。

### 请使用静态库方式

**静态库方式已经验证过 RAM 布局完全可行**：

```
0x20000000 - 0x20000FCC     4,044  .highcode   ← 上电从 Flash 搬到 RAM
0x20000FCC - 0x20001218       588  .data
0x20001218 - 0x20002A98     6,272  .bss
                           ───────
                           10,904  已占用
0x20002A98 - 0x20003000     1,384  .stack（剩余栈空间）
                           ───────
                           12,288  RAM 总量
```

关键指标：

| 项目 | 数值 |
|---|---|
| Flash 占用 | 87,364 字节（85.3 KB，可用 240 KB） |
| RAM 占用 | 10,904 字节（剩 1,384 给栈） |
| 固件文件 | `build/out/ble_uart.hex`（228,150 字节） |
| `FLASH_CMD_*` | 在 RAM `0x20000de6` ✓ |
| 烧录地址 | **只需 `0x00000000` 一个文件** |

### 应用代码不用改

两种方式对外接口完全一致（都通过 `CONFIG.h` → `ch572_ble.h` 提供 API），
应用源码一行都不用动。只是：

| | 静态库方式 | ROM 方式 |
|---|---|---|
| 宏 | 无（默认） | `CH572BLE_ROM=1` |
| 链接 | `-lCH572BLE -lISP572` | `-lISP572` |
| 烧录 | 1 个 hex → `0x0` | 2 个 hex → `0x0` + `0x20000` |
| 固件体积 | 较大（协议栈在应用里） | 较小 |
| **CH572 可用** | **✓ 是** | **✗ 否（RAM 不够）** |

## 五、给后续接手人的提醒

1. **不要再尝试把 ROM 方式搬到 CH572** —— 除非 CH572 有新 RAM 更大的型号。
   这个结论有完整实测数据支撑，不是估算。

2. **如果一定要 ROM 方式**，唯一可能的路径是：
   - 拿到 WCH 用 `-ffunction-sections` 重新编译、且能按需链接的协议栈库
   - 或让 WCH 提供 CH572 专用的 ROM 库（CH59x 那种）
   这两条都超出本工程能做的范围。

3. **`.highcode` 必须放 RAM** 这条规律对两种方式都成立，
   是 WCH 芯片 Flash 操作的基本要求。如果以后有人"为了省 RAM"
   把 `.highcode` 留在 Flash，就会重现本文档开头那个卡死现象。

4. 本文档的排查手段（反汇编定位 + 地址对比）可以先看
   [`实机排查指南.md`](实机排查指南.md)，那里有通用的排查流程。
