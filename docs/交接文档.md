## 一、这个工程是干什么的

### 1.1 起因

WCH 给 **CH592** 提供了「固定地址的 BLE 协议栈镜像」（`CH59xBLE_ROM.hex` + 配套头文件）：
应用不链接协议栈库，只按绝对地址调用，固件因此只有 19 KB 而不是 229 KB。

但给 **CH572** 只给了一个普通的静态库 `libCH572BLE_PERI.a`，没有对应的 ROM 镜像。
另外官方 CH572 SDK 里 **`HAL.c` 是缺失的** —— `HAL.h` 声明了 `CH57x_BLEInit()`，
但整个 SDK 找不到实现（`CONFIG.h` 里甚至还留着 `#include "CH57xBLE_ROM.h"` 这个不存在的文件）。

本工程把这两块补出来了。

### 1.2 交付了什么

| 交付物 | 路径 | 说明 |
|---|---|---|
| **ROM 库镜像** | `lib/CH572BLE_ROM.hex` / `.bin` | 89,316 字节，烧到 `0x20000`，烧一次不动 |
| **应用侧头文件** | `include/CH572BLE_ROM.h` | 94 个可用 API 通过跳转表调用 ROM |
| **HAL 层实现** | `hal/HAL.c` | 补全 `CH57x_BLEInit()` + 6 个硬件回调 |
| **静态库（另一条路）** | `lib/libCH572BLE.a` | 协议栈 + HAL 合并打包，链进应用 |
| **示例工程** | `examples/ble_uart/` | 自定义 GATT 服务 0xFFE0，两种方式各一个 main |
| **一键脚本** | `scripts/make_rom.ps1` | 唯一的 ROM 产物生成入口 |
| **文档** | `docs/` 7 份 | 见 [第六节](#六文档索引) |

### 1.3 实测效果

同一份 `ble_uart` 示例，两种方式对比：

| | 静态库方式 | **ROM 镜像方式** |
|---|---|---|
| 应用 Flash 占用 | 80,864 B | **6,616 B（↓92%）** |
| 应用 hex 文件 | 227,491 B | **18,812 B（↓92%）** |
| 可用栈空间 | 1,384 B | **4,560 B（×3.3）** |
| 芯片总代码量 | 80.9 KB | 93.8 KB（含 ROM 87.2 KB） |

> **注意**：ROM 方式在「芯片总占用」上其实**更多**（多 12.9 KB）。
> 它的价值不在省 Flash，而在 **OTA 升级包从 81 KB 降到 7 KB**，以及升级不动协议栈。

## 三、ROM 方案的核心机制

如果只记一件事，记这个：**跳转表**。

### 3.1 镜像内部布局

```
ROM_BASE = 0x00020000

+0x00    8 字节   镜像标识：魔数 0x43483537（"CH57"）+ 4 字节保留
+0x08   44 字节   UUID 表（22 项 × 2 字节）
+0x34  624 字节   函数跳转表（156 项 × 4 字节）
之后             版本字符串 "CH572_BLE_ROM_V1.0" + 代码 + 只读数据

总计 89,316 字节（87.2 KB），占用 0x20000 - 0x35CE3
```

头部布局由 `rom/rom_link.ld` 里的 `ASSERT` **强制校验**：
```ld
ASSERT(. == ROM_BASE + 0x34, "ROM 头部布局错误：.rom_header 必须正好 0x34 字节")
```
写错直接链接失败，不会等烧进芯片才发现。

### 3.2 应用怎么调用 ROM

`CH572BLE_ROM.h` 把每个 API 定义成对绝对地址的间接调用：

```c
#define FUNCITON_BASE_ADDRESSS   (LIB_FLASH_BASE_ADDRESSS + 0x34)
#define BLE_LIB_JT(n)            (*(uint32_t*)( FUNCITON_BASE_ADDRESSS + (n) * 4 ))

#define tmos_start_task         (( BOOL (*)(tmosTaskID, tmosEvents, tmosTimer) ) BLE_LIB_JT(9))
#define GAPRole_PeripheralInit  (( bStatus_t (*)(void) ) BLE_LIB_JT(46))
```

跳转表下标**刻意沿用官方 `CH59xBLE_ROM.h` 的编号**（由 `rom_jt_extract.py` 抽取），
好处是从 CH592 ROM 工程迁移代码时下标不用改。

**CH572 没有的 43 个 API**（主机角色等）在表里填 `0`，且头文件**完全不定义这些宏** ——
误用会在**编译期**报错，而不是运行时跳到地址 0。

### 3.3 中断怎么处理（最容易漏的一步）

BLE 的基带中断（BB）与链路层中断（LLE）处理函数**在 ROM 里**。
应用的启动文件里这两个中断是「弱定义 + 死循环」，不接管的话射频中断一触发就死在循环里 ——
表现为**「能广播但一连接就死」或「完全连不上」**。

所以 ROM 方式下应用**必须**装钩子：

```c
static rom_app_hooks_t hooks = { .magic = ROM_HOOK_MAGIC };
const rom_handles_t *h = CH572BLE_ROM_GetHandles();   /* 取 ROM 中断入口 */
hooks.ble_irq_handler = h->bb_irq;                    /* 基带中断 → ROM 实现 */
hooks.lle_irq_handler = h->lle_irq;                   /* 链路层中断 → ROM 实现 */
hooks.rtc_irq_handler = RTC_IRQHandler;               /* RTC 由应用处理 */
CH572BLE_ROM_Init(&hooks);                            /* 注册给 ROM */
```

> 官方 CH59x 是把这几个入口写到 RAM 固定地址 `0x20000000 + n*4`，应用再去读。
> 本工程改成 ROM 导出一个取地址函数：省 12 字节 RAM，也不依赖地址约定。

### 3.4 构建流程：五趟链接

**核心矛盾**：跳转表内容（每个 API 的绝对地址）依赖链接结果，而链接又需要跳转表存在。

```
趟 0  准备对象（解包协议栈 54 个 .o + 编译头部/中断转接/兼容桩/6 个驱动）
趟 1  占位链接（跳转表放 156 个 0）         ← ★ 必须关 --gc-sections
趟 2  生成跳转表汇编 + 应用头文件
趟 3  迭代链接 #1（开 --gc-sections）+ 重算跳转表
趟 4  迭代链接 #2（开 --gc-sections）+ 重算跳转表
趟 5  最终链接（不再重算，保证表内容与镜像布局严格一致）
      + 从 .map 读出真实大小 → 生成头文件
      + objcopy 出 hex / bin
```

**为什么趟 1 必须关 `--gc-sections`**：
占位跳转表不引用任何符号，开了 gc 会把整个协议栈判为不可达而裁光 ——
实测可用 API 会从 **94 个掉到 14 个**。

**开 gc 的收益**：趟 1（无 gc）全量 text 约 103 KB；最终约 89 KB，**裁掉约 14 KB 死代码**
（协议栈里"只有主机角色才会走到"的部分）。

## 四、Flash 布局与关键约束

### 4.1 当前布局

```
0x00000 ┌─────────────────────────────────────────┐
        │  app 主体  124 KB（连续一整块）          │  ← 复位向量和代码在一起
0x1F000 ├─────────────────────────────────────────┤
        │  SNV 绑定信息  4 KB（运行期写，不烧录）  │
0x20000 ├─────────────────────────────────────────┤
        │  BLE 协议栈 ROM  87.2 KB（烧一次不动）   │
0x35CE3 ├─────────────────────────────────────────┤
        │  余量  24.8 KB（留给 ROM 将来变大）      │
0x3C000 ├─────────────────────────────────────────┤
        │  芯片固定占用  16 KB（BootLoader+INFO）  │
0x3FFFF └─────────────────────────────────────────┘
```

**设计原则：协议栈靠后、app 占前面一整块连续空间。**
好处是 app 不被 ROM 切成两段 —— 链接脚本只有一个 MEMORY 区域，
复位向量与代码在同一块里，不需要跨段跳板。

### 4.2 三条硬约束（改任何地址前先读这个）

**① SNV 不能落进 ROM 区间**
SNV 是运行期会被**擦写**的区域。与 ROM 重叠会导致「写绑定信息时把协议栈代码擦掉」，
而且**只有上板才会发现**。`run_tests.ps1` 的 4b-2 节专门检查这个。

**② 两种协议栈方式的 `BLE_SNV_ADDR` 必须一致**
`include/ch572_ble.h`（静态库方式）与 `include/CH572BLE_ROM.h`（ROM 方式）当前都是 `0x1F000`。
不一致的话，从一种方式切到另一种时**已配对的绑定信息会全丢**。

**③ 改 ROM 基址必须同步改 `Link_rom.ld`**
```
新 FLASH_ROM_END = 新 ROM 基址 − SNV 大小
```
当前 = `0x20000 − 0x1000` = `0x1F000`。构建日志会打印这一行。

### 4.3 想改 ROM 基址怎么办

先用探测模式量一下（因为 ROM 大小会随基址微调，有循环依赖）：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\make_rom.ps1 -Probe
```

它会输出推荐基址和对应的 app 空间，然后把结果填回去：

```powershell
scripts\make_rom.ps1 -RomBase 0x00020000
```
```ld
/* src/Ld/Link_rom.ld */
FLASH_ROM_END = 0x0001F000;
```

**注意**：探测模式用的是第 1 趟（未开 gc）的尺寸，比最终镜像大约 13 KB ——
这是**保守上界**。基址不能设得太高，否则占位链接就放不下了（实测 `0x26000` 会失败）。

## 五、工具链

**只支持 MounRiver Studio 自带的 WCH 定制工具链**（脚本会自动探测）：

```
D:\MounRiver\MounRiver_Studio2\resources\app\resources\win32\
    components\WCH\Toolchain\RISC-V Embedded GCC12\bin\riscv-wch-elf-gcc.exe
    →  xPack GNU RISC-V Embedded GCC 12.2.0
```

**为什么只能用它**：协议栈源码用了两个 WCH 扩展，通用 RISC-V 工具链不认识：

| 扩展 | 用在哪 | 通用工具链 |
|---|---|---|
| `mcpy` 青稞私有快速内存拷贝指令 | `core_riscv.h` 的 `__MCPY()` | ✗ 报 `unrecognized opcode` |
| `WCH-Interrupt-fast` 中断硬件压栈 | `CH57x_common.h` 的 `__INTERRUPT` | ✗ 不认识该属性 |

实测 WCH 工具链真的生成了 `mcpy`（3 处），而协议栈自带的 `tmos.o`、`ll_connect.o`
里**也含 `mcpy`** —— 说明 WCH 当初就是用这个工具链编的库。

找不到工具链时脚本**直接报错退出**（不会悄悄退回通用工具链去编一个有问题的产物）。

## 七、能力边界（重要，别做无用功）

逐符号比对 `libCH59xBLE.a`（CH592）与 `libCH572BLE_PERI.a` 的结论：

| 能力 | CH572 | CH592 |
|---|---|---|
| BLE 从机 / 自定义 GATT / 配对绑定 / 广播者 | ✅ | ✅ |
| 连接参数更新 / MTU 协商 / PHY / RSSI | ✅ | ✅ |
| 2.4G 私有协议点对点 | ✅ | ✅ |
| **主机（Central，主动扫描发起连接）** | ❌ | ✅ |
| 观察者 / GATT 客户端 / 多从机并发 | ❌ | ✅ |
| 扩展广播 / 周期同步（BLE 5.x）/ 跳频 | ❌ | ✅ |

**根因**：`libCH59xBLE.a` 有而 `libCH572BLE_PERI.a` 没有的 **649 个符号全部集中在主机侧**
（HCI 命令层、链路层扫描/连接状态机、GATT 客户端）。这是**芯片固件里就没有这部分代码**，
不是"库没编译进去"。加上 CH572 只有 12 KB RAM、无 BLE ROM 区，硬做也铺不开。

### 决策规则

> **你的设备是「被别人连」还是「主动去连别人」？**
> 被别人连 → CH572 完全够用。
> 主动去连别人 → 必须换 CH592。

本工程用编译期能力宏把这条边界固化了，误用主机 API 直接编译报错：

```
error: call to '_ch572_ble_missing_api' declared with attribute error:
       CH572 BLE 固件库不提供该 API，请检查平台能力宏 CH572_BLE_HAS_xxx
```

② build\out\ble_uart-rom.hex  → 0x00000000 起     （以后只更新这个）

## 九、踩过的坑（改代码前先看）

这一节是**用真实调试时间换来的**，能省掉重复踩坑。

### 9.1 构建脚本相关

| 现象 | 根因 | 解法 |
|---|---|---|
| `ar` 解包出 0 个文件，**但退出码是 0** | MRS2 工具链路径带空格，`cmd` 解析「引号包裹路径 + `>` + `2>&1`」时切错参数 | 生成临时 `.bat` 再执行（已内建） |
| GCC 报「找不到源文件」，路径少了反斜杠 | GCC 的 `@响应文件` 语法把 `C:\a\b.c` 当转义符吃掉成 `C:ab.c` | 不用响应文件，把完整命令行写进 `.bat`（已内建） |
| `意外的属性 CmdletBinding` 之类莫名语法错 | `.ps1` 缺 BOM（按 GBK 解析）**或**多了一个 BOM | `python tools\fix_ps1_encoding.py` |
| 自动探测工具链永远失败 | `Find-Gcc` 里变量名不一致（`$exeNames` vs `$names`） | 已修；改这类代码后跑一次自检 |
| ROM 链接报 `will not fit in region ROM` | 第 1 趟占位链接比最终镜像大约 13 KB | 用 `-Probe` 算推荐基址，或把 ROM 基址往前挪 |

### 9.2 ROM 镜像相关

| 现象 | 根因 | 解法 |
|---|---|---|
| 头部布局错位（UUID 排到魔数前面） | GNU ld 在同一输出段内按**输入段名字母序**排列 | 拆成 `.rom_magic` / `.rom_uuid` 两个命名段 + `ASSERT` 校验 |
| 魔数位置不对 | 两个 `uint32_t` 变量在 `-O` 下顺序不保证等于源码顺序 | 合成一个 `uint8_t _rom_magic[8]` 数组 |
| 开 gc 后可用 API 只剩 14 个 | 占位跳转表不引用符号，协议栈被全裁 | 趟 1 必须关 `--gc-sections` |
| 生成了一堆多余的数据桩 | 只收集 `STB_GLOBAL` 符号，把 LOCAL 的 `.bss`（`gapRole_state` 等）误判为缺失 → 桩覆盖真实数据 | `rom_stub_gen.py` 改成收集任何有段名的符号 |
| `undefined reference to TMOS_SystemProcess` | 该 API 不在 CH59x 的 ABI 清单里 | `rom_gen.py` 给本工程扩展 API 分配表尾空闲下标 |
| 头文件里 CODE 大小显示「约 0 KB」 | 头文件在迭代链接阶段生成，那时还不知道最终大小 | 改成最终链接后从 `.map` 读真实大小再生成 |

### 9.3 内存布局相关

| 现象 | 根因 | 解法 |
|---|---|---|
| 静态库方式栈只剩 224 字节 | `BLE_MEMHEAP_SIZE = 6144` 太大 | 降到 `512*10 = 5120` |
| **写绑定信息会擦掉协议栈** | SNV 地址落进了 ROM 区间 | `run_tests.ps1` 4b-2 节专门检查这个 |
| 换协议栈方式后配对信息丢失 | 两种方式的 `BLE_SNV_ADDR` 不一致 | 两个头文件都固定用 `0x1F000` |
| 自检误报「SNV 与 ROM 重叠」 | 测试脚本里写死了 SNV 大小 | 改成从 `Link_rom.ld` 读 `SNV_SIZE` |

### 9.4 分析工具相关

| 现象 | 根因 | 解法 |
|---|---|---|
| `isa_check.py` 报「17 条浮点指令」 | 直接线性扫描整个 `.text`，把字符串/跳转表当指令 | 先从符号表取 `STT_FUNC` 区间，只扫真实函数 |
| `mem_layout.py` 只解析出 `.data`/`.bss` | ELF 段表解析在模块内重复调用时结果不一致 | 重写成基于程序头 PT_LOAD 统计 Flash + 段头统计 RAM |
| 符号表文件解析失败 | PowerShell 的 `*>` 按 UTF-16LE 落盘 | 用 `cmd /c ... > file` 重定向 |

### 9.5 HAL 初始化（实机搜不到信号的那次）

**现象**：ROM 镜像与应用固件都烧录成功，但手机搜不到任何蓝牙信号。

**排查过程**：
1. 先对比官方示例的 `main()` —— 初始化顺序一致，排除顺序问题。
2. 找官方 `CH57x_BLEInit()` 的实现 —— 它在 **`HAL/MCU.c`**，不在 `HAL.c`！
   （一开始在 `HAL/HAL.c` 里找不到，以为官方真的没给）
3. 逐行对比官方 `MCU.c` 与本工程 `hal/HAL.c`，发现 4 项遗漏 + 2 个参数错误。

**根因**（按危害排序）：

| 项目 | 官方 | 本工程（错） | 后果 |
|---|---|---|---|
| `R32_MISC_CTRL` bit24-29 | `0xe` | **完全没设** | ★ 射频不工作 |
| `__SysTick_Config` | 有 | **没有** | 时基/随机数失效 |
| `g_LLE_IRQLibHandlerLocation` | 设为 LLE ISR | **没有** | 协议栈找不到 ISR |
| `PFIC_SetPriority(BLEL_IRQn,0xF0)` | 有 | **没有** | 连接事件可能丢 |
| `cfg.WindowWidening` | `120` | `2` | 射频启动窗口不足 |
| `cfg.MacAddr` | `GetMACAddress()` | 全 0 | MAC 无效 |

**修复**：见 `hal/HAL.c` 的 `CH57x_BLEInit()`（14 个编号步骤，每步都注明了
为什么不能省）。ROM 专属的部分用 `#ifdef CH572BLE_ROM` 包住，
`rom_handles_t` 相应增加了 `lle_lib_irq` / `bb_lib_irq` 字段。

**验证方式**（重要，以后改 HAL 都该跑）：

```powershell
python tools\verify_hal_fixes.py
```

反汇编确认 5 个关键项真的编进了固件。实测：
- `0x40001040` 写 `0x57`/`0xA8`（安全访问签名）→ 然后读改写 `0x40001048`
- `lui a5,0xe000f` + `sw`（SysTick 配置）
- `sb a4,1045(a5)`，`a5=0xE000E000` → 写 `0xE000E415` = PFIC IPRIOR[21]（BLEL_IRQn）
- `tmos_memcmp` 版本比较调用

**教训**：
> 官方实现可能不在你以为的文件里。CH572 的 `CH57x_BLEInit()` 在
> `EVT/EXAM/BLE/HAL/MCU.c`。以后找官方参考实现，要**全目录搜索函数名**，
> 不要按文件名猜。

## 十、这个工程没做什么

**明确边界，避免误判。**

1. **没有重新编译协议栈。** WCH 未公开 BLE 协议栈 C 源码。本工程用的是官方
   `libCH572BLE_PERI.a` 里的**二进制对象**，只是把它们**重定位到固定地址**、
   补上跳转表与 HAL、生成镜像。
2. **没有给 CH572 增加主机能力。** 见第七节，这是芯片固件的限制。
3. **ROM 镜像没有在 CH572 实机上烧录验证过。** PC 侧完成了全量编译、链接、
   跳转表逐项一致性校验、指令集兼容性校验、内存布局检查、31 项自检，
   但**当前环境没有 CH572 EVT 板**。
4. **OTA 方案是规划推算，没有实机验证。** `docs/内存布局与OTA规划.html` 里的
   分区数值：方案 A 来自官方示例原值，方案 B/C 是按实测 ROM 大小推算的。

## 十一、下一步建议

按优先级排序：

### 11.1 必做：实机验证（最高优先级）

这是目前**唯一没做的关键环节**。建议步骤：

1. 用 `make_rom.ps1` 生成 ROM 镜像，确认 `lib/CH572BLE_ROM.hex` 已更新
2. 烧 `CH572BLE_ROM.hex` 到 `0x20000`，烧 `ble_uart-rom.hex` 到 `0x0`
3. 用手机 App（如 nRF Connect）搜 `CH572-BLE-UART`
4. 验证：广播可见 → 能连接 → 读 0xFFE1 → 写 0xFFE3 → 收到 0xFFE4 通知
5. **特别验证配对绑定**：配对一次 → 断电 → 上电 → 应仍是已绑定状态
   （这条验证 SNV 地址配置正确）
6. 顺便对比静态库方式（`ble_uart.hex`）是否行为一致

> 如果第 5 步失败（重新上电后需要重新配对），说明 SNV 没生效 ——
> 检查 `BLE_SNV_ADDR` 是否与 `Link_rom.ld` 里的 `SNV_ADDR` 一致。

### 11.2 可选：OTA 落地

三条路线见 `docs/内存布局与OTA规划.html` 第 4 节。简要：

| 方案 | 升级包 | 回滚 | 工作量 |
|---|---|---|---|
| A 不用 ROM，官方双镜像 | 81 KB | ✅ | 小（官方示例直接改） |
| B ROM + A/B 双镜像 | **7 KB** | ✅ | 中（要自研 JumpIAP / 刷写） |
| C ROM + 单下载区 | **7 KB** | ❌ | 中 |

**注意**：用 ROM 后 Flash 尾部被占，官方 OTA 的 108K+108K 布局**放不下了**，
必须按新布局重排。

### 11.3 可选：工程化改进

| 事项 | 说明 |
|---|---|
| ROM 基址自动化 | 让 `make_rom.ps1` 把最终结束地址写进 `Link_rom.ld` 或生成 `rom_layout.h`，避免手工同步 |
| 合并 hex | 把 ROM + 应用合成一个 hex，产线一次烧完（现在是两个独立 hex） |
| MRS 工程模板 | 目前 `make_mrs_project.ps1` 靠字符串替换生成 `.cproject`，可以做成模板 |
| 上板自动化 | 如果有 WCH-Link 命令行工具，可以把烧录 + 复位 + 观察串口做成脚本 |

### 11.4 如果需求超出 CH572 能力

需要主机（Central）、GATT 客户端、多连接、BLE 5.x 扩展广播、跳频 ——
**换 CH592**（448 KB Flash / 26 KB RAM / 有官方 ROM 方案），
本工程的 ROM 方案思路可以整体迁移过去。
