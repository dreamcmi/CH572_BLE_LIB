CH572 固化协议栈工程 把 WCH 的 libCH572BLE_PERI.a 重定位到 Flash 固定地址，生成跳转表供独立应用调用

✅ 2026-10-10 实机验证通过 调试版固件在 CH572 上电后正常出日志、正常广播；手机能搜到 CH572-BLE-UART、能连接， 并成功收到 GAP_SCAN_REQUEST_EVENT（扫描端 4F:3D:7C:D5:A8:B4）。 这是本工程第一次实机跑通。

这是什么

CH572 是 WCH 的一款 BLE 从机芯片，官方只提供静态库 libCH572BLE_PERI.a（约 89 KB 代码）。 本工程把这份协议栈预链接成一个固定地址的 Flash 镜像，放在 0x20000， 并在镜像头部放一张跳转表。应用从此不再链接协议栈库，而是通过绝对地址调用它。

这样做换来的核心收益只有一个，但很关键：应用固件从 86 KB 缩到 12.5 KB，OTA 升级包同比例缩小，而且升级不动协议栈。

收益

应用 12.5 KB

相比静态库方式的 86 KB，缩小约 85%。OTA 每次只传应用段。

代价

芯片总代码变多

92.7 + 12.5 = 105 KB，比纯静态的 86 KB 多约 19 KB。协议栈与应用的公共部分无法共享。

约束

RAM 只剩 1,224 字节栈

CH572 总共 12 KB SRAM，协议栈堆占 5 KB。这是本工程最紧的资源。

Flash 与 RAM 布局

三个最关键的设计点

设计点 1

跳转表：应用与协议栈的唯一接口

镜像头部 +0x34 起是一张 164 项 × 4 字节的跳转表。应用侧头文件把每个 API 定义成对表里某一项的间接调用：

#define BLE_LIB_JT(n)  (*(uint32_t*)(FUNCITON_BASE_ADDRESSS + (n) * 4))
#define tmos_rand      (( uint32_t (*)(void) ) BLE_LIB_JT(1))

43 个本平台不提供的 API 在表里是 0，并且在头文件里完全没有宏 —— 误用是编译/链接期报错，不会运行时跳到地址 0。

设计点 2

ROM 没有上电入口，应用要替它初始化

ROM 镜像里有自己的 .data 和 .bss（共 1,184 字节），但它没有复位向量 —— 没人替它搬初值、清零。

所以应用必须：预留这段 RAM（改链接脚本的 ORIGIN）、在调用任何 ROM 函数前搬 .highcode/.data、清 .bss、执行 fence.i。

踩过的坑 漏掉这一步的后果是协议栈初始化直接卡死在 BLE_LibInit，而且没有任何报错。
设计点 3

BLE 中断走 PFIC VTF，不走向量表

CH572 的 BLEB/BLEL 中断由协议栈通过 PFIC VTF（Vector-Table-Free）通道 #2/#3 接管，硬件直接从 ROM 里的真 ISR 进入。

这意味着中断向量表里那两项是死代码 —— 早期版本把"ROM 搜不到设备"归因于"向量表悬空"，方向完全错了。

→ 看运行流程图里的中断路径

设计点 4

ROM 里的初始化会被周期重放

BLE_RegInit()（周期校准调用）内部会再跑一次 LLE_DevInit/BB_DevInit，从而把 VTF 重写回 ROM 的地址。

应用侧任何"抢过来"的状态都必须挂在同一个周期上重新确认，否则只能活到第一次重放 —— 这是实机上真实踩到的坑。
