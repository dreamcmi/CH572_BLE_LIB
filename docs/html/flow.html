为什么要五趟链接

跳转表的内容（每个 API 的真实地址）来自链接结果，而跳转表的长度又会影响后面所有符号的地址 —— 这是一个循环依赖。解法是迭代：

趟做什么为什么不能省
1用全 0 占位表链接，采符号地址必须关 --gc-sections：占位表不引用任何符号，开着 gc 会把协议栈整个裁掉（可用 API 从 94 掉到 14）
2按第 1 趟地址生成真实跳转表表变长了，后面符号会后移
3 / 4开 gc 重新链接 + 重算表开 gc 能裁掉约 14 KB 只服务主机角色的死代码；迭代两次即收敛（实测趟 2/3 产物 SHA256 完全相同）
5最终链接，不再动跳转表保证"表内容"与"镜像布局"严格一致，而不是差一轮迭代
占位表长度为什么写死 164 真实项数由 rom_gen.py 决定：以 ABI 参考头文件的最大下标 +1 为起点做 4 项对齐， 再为 5 个扩展 API 扩容并重新对齐。参考头文件本身有重复下标（条目 137 个但最大下标 140）， 算不准，所以占位表直接取当前实测的真实项数。 脚本会用 ABI 参考估一个下界并在不够时警告 —— 若最终链接报 rom_jt size mismatch， 就调大 make_rom.ps1 里的 $JT_PLACEHOLDER_ENTRIES。
