CH572 固件文档 总览 快速上手 运行流程图 固件介绍 纯 RF 收发

CH572 纯 2.4G 收发固件 只做射频收发，不使用蓝牙协议栈 —— 两条路线可选

这是另一条独立路线 和前面四页讲的 BLE 固化协议栈方案没有关系：本固件链的是 WCH 的纯 RF 库 libCH57xRF.a，不初始化 TMOS、不需要 BLE 内存堆、不涉及 GAP/GATT/SM。

一、这是什么

WCH 的 CH572 EVT 包里有两个独立的库。本文走第二条：把 libCH57xRF.a 预链接到固定地址，镜像头部放一张跳转表， 应用从此不链接 RF 库、只通过绝对地址调用它。

库大小对象数用途
libCH572BLE_PERI.a613 KB54完整 BLE 协议栈（前面四页讲的）
libCH57xRF.a24 KB4纯 2.4G 收发（本页）

二、架构

思路与 BLE 的固化协议栈完全一样：把 RF 库预链接到固定地址， 应用不链接库、只通过跳转表调用。好处是应用里完全没有 RF 库的代码， 以后改应用只传 1,660 字节。

2.1 和 BLE 那套的三个关键差异

BLE 固化协议栈RF 固定地址镜像
跳转表槽位 必须沿用 WCH 官方下标，43 个缺失 API 要留空槽 13 个 API 全部可用，连续编号、零空槽
为什么 官方 ABI 契约（BLE_LIB_JT(48) 必须还是那个函数） RF 库没有官方 ABI 头，不受任何既有编号约束
版本串 必须自己造（要参与 VER_FILE 校验，造错会卡死） 直接引库自己的 VER_RF_LIB，天然一致
UUID 表有（GATT 标准 UUID，22 项）无
兼容桩有（10 个，库被裁过符号）无（nm -u 为空）
这是本工程唯一一处"不需要为缺失 API 预留位置"的地方 BLE 那边留空槽是被 WCH 官方 ABI 绑住的；RF 这边没有这个约束 —— 13 个 API 连续排，跳转表就 52 字节，零浪费。

2.4 应用侧必须做对的三件事

#做什么漏掉的后果
1校验镜像魔数（RF_RomImagePresent()） 镜像没烧时会跳到空白 Flash，症状极难查
2搬运镜像 RAM（RfRomRam_Init()）
搬 3,112 B .highcode + 清 48 B .bss		 跳到一片空白 RAM（全 0 = 非法指令）→ HardFault
3中断走跳转表：
LLE_IRQHandler → RF_LleIrqHandler() → RF_JT(12)		 中断悬空，收不到包
为什么必须走跳转表，不能直接调 镜像不参与应用的链接，BB_LibIRQHandler / LLE_LibIRQHandler 这些符号在应用里根本不存在，所以只能运行时从跳转表取地址。

四、中断路径

★ 这是两条路线最容易混淆的地方 ★ BLE 方案下，协议栈会通过 PFIC VTF 抢走 BLEB/BLEL 中断， 应用的向量表包装函数其实是死代码。
纯 RF 库没有这一步 —— 所以包装函数是真正生效的路径，而且必须自己使能中断。

六、两个必须知道的坑

坑 1

两个头文件的 LL_TX_PWR_* 数值不一样

宏CH572rf.hBLE 头
..._MINUS_10_DBM0x050x04
..._MINUS_8_DBM0x070x06
..._MINUS_5_DBM0x0A0x08

两个头绝对不能同时包含。重定义警告会被忽略，实际生效的是先包含的那个 —— 而 libCH57xRF.a 是按 RF 头的值编的，用错值就设错发射功率。

本工程的处理：RF 头放独立目录 include/rf/； rf_rom_app.c 刻意不 include CONFIG.h，切断 BLE 头那条链。

坑 2

纯 RF 库不自己接管中断

BLE 方案下协议栈通过 PFIC VTF 直接抢走 BLEB/BLEL，应用包装函数是死代码。

纯 RF 库没有这一步，所以必须自己写包装函数：

__INTERRUPT __HIGH_CODE
void LLE_IRQHandler(void) { LLE_LibIRQHandler(); }
__INTERRUPT __HIGH_CODE
void BB_IRQHandler(void)  { BB_LibIRQHandler();  }

并显式使能 PFIC_EnableIRQ(BLEB_IRQn) / PFIC_EnableIRQ(BLEL_IRQn)。
漏掉的症状：发送好像成功，但接收端永远收不到。

七、为什么能这么小

WCH 的 CH572 EVT 包里其实有两个独立的库：

库大小对象数用途
libCH572BLE_PERI.a613 KB54完整 BLE 协议栈
libCH57xRF.a24 KB4纯 2.4G 收发

libCH57xRF.a 只有 4 个对象（rf_basic.o / rf_ip.o / rf_role.o / rfend.o），代码合计 5,662 字节。 实测它完全自足：

检查结果
nm -u 未定义符号空
需要的 4 个全局变量（gptrBBReg 等）自带
是否依赖 TMOS完全不依赖
是否依赖 BLE 内存堆不需要

导出的 API

RFRole_BasicInit(&conf)    // 初始化，注册回调
RFIP_StartTx(&txParam)     // 发一包
RFIP_SetRx(&rxParam)       // 收一包（一次一收，收完要重新武装）
RFIP_SetChannel(ch)        // 换频道
RFRole_Stop() / RFRole_Shut()
BB_LibIRQHandler() / LLE_LibIRQHandler()          // 真 ISR
RFEND_TXCtuneSet/Get() / RFIP_SetTxPower() / RFIP_Calibration()
为什么不能在 BLE 库里"裁"出 RF-only RF_RoleInit（BLE 库里那个）内部调 BLE_IPCoreInit —— RF 和 BLE 共用同一套底层射频初始化。而 libCH572BLE_PERI.a 是预编译二进制， --gc-sections 只能在函数级裁剪，裁不动模块级（实测只砍掉 9.6%）。
所以正确做法是换库，不是裁库。

上板第一步建议

  1. 烧 TX 到板 A、RX 到板 B，接好串口
  2. 先看两边初始化日志 —— 确认打印出的 freq / addr 一致
  3. 接收端应开始打印递增的 seq
  4. 如果收不到，按顺序查：
    • 两端 RF_APP_FREQ_KHZ / RF_APP_ACCESS_ADDR / RF_APP_PHY_MODE 是否一致
    • R32_MISC_CTRL 的 bit24-29 是否被设成 0x0E
    • 有没有漏 PFIC_EnableIRQ(BLEB_IRQn/BLEL_IRQn)
    • 天线是否接好（CH572 射频是内部 PA，但需要外部匹配网络）
  5. 镜像方式特有的两条：
    • 镜像烧到 0x10000 了吗？串口应打印 [rf_rom] 镜像版本：CH57x_RF_BASIC_LIB_V1.2.0； 若打印"镜像不存在或魔数不对"，就是镜像没烧或烧错地址
    • 串口有 [rf_rom] 已搬运镜像 RAM 这一行吗？ 没有就是 RfRomRam_Init() 被跳过或调用顺序错了
