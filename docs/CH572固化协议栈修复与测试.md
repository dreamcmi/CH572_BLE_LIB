## 已定位并修复的故障

1. **ROM 高速代码没有正确装入 SRAM。** 独立镜像没有 reset 入口，应用必须复制 ROM 的普通 `.highcode` 和 `.data`，清零 `.bss`，然后执行 `fence.i`。生成器现在从 ELF 的 PT_LOAD 段计算包含偏移的 LMA；生成失败会终止构建，不再按“ROM RAM 为零”继续链接。
2. **release 会丢失中断钩子注册。** 原来的 `PRINT(... CH572BLE_ROM_Init(&hooks))` 在关闭 DEBUG 后被空宏整体删除。现在无条件调用初始化，再按需打印。
3. **BB/LLE 中断入口使用普通 C 返回。** 应用新增 `hal/rom_irq.c`，用 WCH fast interrupt ABI 和 `mret` 返回，内部普通调用库 ISR。向量表放在 Flash 0x400，省去 SRAM 内 1024 字节对齐造成的浪费；ROM 转接桩也使用正确中断属性。
4. **启动中断与复制顺序不完整。** startup 首先关闭 MIE，复制应用 highcode 后执行 `fence.i`，先设置 `mtvec`。ROM 应用以中断关闭状态进入 main，初始化 ROM RAM 和钩子后再开启中断。新固件保留调试引脚。
5. **ROM 和应用重复保留 ISP 代码，RAM 预算过紧。** ROM 跳转表新增 `FLASH_EEPROM_CMD`，应用 `rom_flash.c` 转发调用。擦写与等待的底层 ISP 函数在复制到 SRAM 的代码区运行。拆分驱动中聚合的 highcode 段后，未使用函数可以被链接器回收。
6. **SNV 回调的长度和擦除单位错误。** Flash 回调的 `num` 按 32 位字计，读写长度改为 `num * 4`；物理擦除按 4KB 扇区。逻辑块可保持 256 字节，但独占整个物理扇区，拒绝越界或多个小块共享扇区的配置。
7. **HAL 事件和校准流程不完整。** 先注册 TMOS task，再安排事件；按实际事件位清除标志，恢复官方 RF/LSI 周期校准和 `TMOS_TimerSet`。发布版 SysTick 使用官方自由计数配置，调试版 ISR 使用正确中断 ABI。
8. **自检错误接受不完整的跳转表。** 现在按生成的 164 项检查，允许确实位于已复制 RAM highcode 内的指针；所有项均与 ELF 符号比较。合并 HEX 还做校验和及内容回读核对。诊断读取函数入口改用字节读取，避免半字对齐入口触发非对齐字访问。

历史文档把全部 `.highcode*` 都算作必须驻留 RAM，或把 ISP 的正常重定位误判成固定 RAM 调用。当前布局按可工作的静态链接策略处理：普通 `.highcode/.highcode.*` 在 RAM，`.highcode_fast/.highcode_lp` 按原静态策略放在 Flash。ROM 链接关闭 relax，并检查最终反汇编没有依赖应用的 `gp`；应用仍使用自己的 `gp`。

## 中断走的是 PFIC VTF，不是中断向量表（重要更正）

第六次排查更正了一个会误导判断的结论。**CH572 的 BLEB/BLEL 中断不经过中断向量表，走 PFIC 的 VTF（Vector-Table-Free）通道 #2/#3。** 证据是 ROM 镜像的反汇编：

```asm
000357c6: li   a5,20                     # BLEB_IRQn
000357c8: sb   a5,83(a3)                 # a3=0xE000E000 → VTFIDR[3] = 20
000357cc: auipc a5,0x1ffcb
000357d0: addi  a5,a5,-1776              # 0x200000DC
000357d4: ori   a5,a5,1                  # <BB_IRQLibFunction> | ENABLE
000357d8: sw   a5,108(a3)                # VTFADDR[3]
; LLE 同款：sb 21,82(a4) → VTFIDR[2]=21；VTFADDR[2]=0x200004B6 <LLE_IRQFIOFHandler>
```

协议栈在 `BB_DevInit` / `LLE_DevInit`（由 `BLE_LibInit` 内部调用）里自己写这两个寄存器，所以硬件直接从 ROM 里的真 ISR 进入：

```
VTFADDR[2/3] → LLE_IRQFIOFHandler / BB_IRQLibFunction（__INTERRUPT，以 mret 结束）
             → LLE_IRQLibHandler / BB_IRQLibHandler（普通函数，以 ret 结束）
```

这条链在 ROM 内部闭环、ABI 正确，**不依赖应用**。由此得到三条必须记住的结论：

1. **上一版文档把"ROM 搜不到设备"归因于"中断向量悬空"是错的。** `Link_rom.ld` 里 `.vectors` 的 BLEB/BLEL 两项、`hal/rom_irq.c` 的包装函数、ROM 的转接桩与钩子表，在这个配置下**都不会被硬件取用**，是死代码。真正的修复来自 RAM 初始化、MISC_CTRL 射频位、WindowWidening 等项。
2. **静态库版本里 BB/LLE 向量槽指向 `j .` 死循环，同样无害**，不要误判成缺陷。
3. **调试版心跳里的"BLE中断计数"必须先把 VTF 抢回来才有效。** 否则 `g_dbgBleIrqCount` 恒为 0，而旧验收文档却要求它"持续变化" —— 会把实机排查直接带偏。

### 但这个计数会被周期校准踢掉 —— 实机踩到的第二个坑

首次实机跑通时日志出现了矛盾：设备广播、连接、扫描请求**全部正常**，但
`BLE中断=0`，且 `VTF 入口` 显示的仍是 ROM 的原始地址（`[2]=0x200004B7`、
`[3]=0x200000DD`）而不是应用包装函数。

**根因**：`BLE_RegInit()` 内部会再调一次 `LLE_DevInit` + `BB_DevInit`
（ROM 反汇编 `0x2A296` / `0x2A2A6`），而这两个函数**每次都把 VTFADDR 重写回
ROM 自己的 ISR**。周期校准由 `HAL_REG_INIT_EVENT` 驱动，首次在 `HAL_Init()`
后 800 tick（约 500 ms）触发 —— 所以只在 `main()` 里武装一次，
**首次校准就把它覆盖掉了**。之后计数永远是 0，而设备功能完全正常。

**修复**：把武装逻辑集中到 `hal/rom_irq.c` 的 `HAL_RomVtfRefresh()`，
它只在 `VTFADDR` 确实不等于应用包装地址时才写（正常路径零开销），
并在两个点调用：

| 调用点 | 作用 |
|---|---|
| `main()` 里 `CH57x_BLEInit()` 之后 | 首次武装，让上电到首次校准之间也能计数 |
| `HAL_ProcessEvent()` 的校准分支里 `BLE_RegInit()` 之后 | **关键** —— 抵消协议栈的重写 |

发布构建里 `HAL_RomVtfRefresh()` 是空实现，不产生代码，保持 ROM 出厂路径。

```c
/* hal/rom_irq.c —— 只在确实被改回 ROM 时才重新武装 */
uint8_t HAL_RomVtfRefresh(void)
{
#ifdef DEBUG
    uint8_t fixed = 0;
    if(PFIC->VTFADDR[2] != (((uint32_t)LLE_IRQHandler) | 0x1u))
    { SetVTFIRQ((uint32_t)LLE_IRQHandler, BLEL_IRQn, 2, ENABLE); fixed = 1; }
    if(PFIC->VTFADDR[3] != (((uint32_t)BB_IRQHandler)  | 0x1u))
    { SetVTFIRQ((uint32_t)BB_IRQHandler,  BLEB_IRQn, 3, ENABLE); fixed = 1; }
    return fixed;
#else
    return 0;
#endif
}
```

于是中断链在稳态下是
`VTFADDR[2/3] → 应用包装函数(mret) → 计数 hook → ROM 真 ISR(ret)`，
计数才真正可用。**校准发生时若检测到被改回，还会打一行
`校准后 VTF 被协议栈改回 ROM，已重新武装`** —— 这行日志本身就是"校准真的跑了"
的证据。

> 教训：**ROM 里的初始化函数不是一次性的。** 只要某个 ROM 函数在运行期被周期
> 调用，它做的所有寄存器配置都会周期性重放。应用侧任何"抢过来"的状态都必须
> 挂在同一个周期上重新确认，否则只能活到第一次重放。

调试版心跳会打印真实生效的 VTF 项，便于一眼判断：

```
[心跳 19] tick=... 间隔=... BLE中断=48213
      VTF 入口: [2]=0x20001205 (有代码)  [3]=0x200011F9 (有代码)
      VTF 中断号: [2]=21  [3]=20（期望 21 / 20）
      向量表[20]=0x200011F8 [21]=0x20001204（VTF 生效时不走这里）
```

- `VTF 入口` 是 `0x200012xx` → 应用包装函数在跑，计数有效。
- `VTF 入口` 是 `0x200004B7` / `0x200000DD` → 又被改回 ROM 了，计数必然是 0
  （但功能仍然正常，别据此判断射频有问题）。

## 低功耗（HAL_SLEEP）当前状态

**默认关闭**（示例 `HAL_SLEEP=FALSE`）。本次补齐了打开它所需的两处缺失，但**尚未实机验证**：

| 缺什么 | 状态 |
|---|---|
| `SLEEP_RTC_MIN_TIME` / `SLEEP_RTC_MAX_TIME` | 已补进 `include/RTC.h`（官方在 SDK 的 `HAL/include/CONFIG.h` 里，本工程原缺，导致 `HAL_SLEEP=TRUE` 直接编译失败） |
| `RTC_MAX_COUNT` | 从 `hal/RTC.c` 上移到 `include/RTC.h`，否则 `hal/SLEEP.c` 看不到 |
| `HAL_SleepInit()` 调用 | 已在 `HAL_Init()` 里补上（官方在 `HAL/MCU.c` 里调）。漏它的后果是 `R8_SLP_WAKE_CTRL` 的 `RB_SLP_RTC_WAKE` 不置位，睡下去没有唤醒源 |
| `HAL_TimeInit()` 调用顺序 | 已改到 `tmos_start_task()` **之前**，与官方 `HAL_Init` 一致。以前顺序反了：TMOS 时钟还没建立就排程首次校准事件，触发时刻不确定 |

启用方法（注意 `-Defines` 里一个 `-D` 不能带逗号）：

```powershell
powershell -Command "& '.\scripts\build.ps1' -Target rom `
    -Defines @('HAL_SLEEP=TRUE','BLE_MEMHEAP_SIZE=4096')"
```

**为什么必须同时把堆降到 4,096：** 打开睡眠会通过 `HAL_TimeInit() → RTC_InitClock()` 间接引入 newlib 浮点支持（`RTC.h` 的 `US_TO_RTC` 等宏是 double 运算），实测多占约 0x90 = 144 字节 RAM。实测数据：

| 配置 | 链接栈余量 | 结果 |
|---|---|---|
| 堆 5,120，睡眠关 | 1,224 字节 | ✅ 当前默认 |
| 堆 5,120，睡眠开 | 1,080 字节 | ❌ 低于 1,024 下限，链接失败 |
| 堆 4,608，睡眠开 | 仍不足 | ❌ 链接失败 |
| **堆 4,096，睡眠开** | **1,168 字节** | ✅ 链接通过 |

**上板前必须确认的三件事**（任一不成立都要回头改）：

1. **PFIC VTF 寄存器在睡眠后是否保持。** 这是本项目最不确定的一点 —— BLE 中断靠 `VTFADDR[2]/[3]`（见上面 VTF 一节），如果睡眠会清掉这两个寄存器，唤醒后 BLE 中断就没了。上板第一件事就是看唤醒后 `BLE中断=` 计数是否继续增长。
2. **唤醒后连接事件是否准时。** 保持连接运行 3 分钟以上，覆盖默认 120 秒周期校准，观察有没有掉线或数据错乱。
3. **实测休眠电流。** `CH57x_LowPower` 用的是 `RB_PWR_RAM12K | RB_PWR_EXTEND | RB_XT_PRE_EN`，ROM RAM 区（0x20000000–0x200011E4）与应用 RAM 都在 12 KB 保留范围内，理论上不会掉电丢数据，但需要万用表确认。

## 用户实机验收

1. 首次下载 **`build/out/ble_uart-rom-debug-combined.hex`**。HEX 已包含应用和协议栈，按内置地址一次下载；不需要人为添加偏移。它不包含 SNV 初始化数据。初次测试若需干净绑定状态，可先擦除旧固件和旧 SNV 再下载整个合并文件。
2. UART 使用 **PA3 TX / PA2 RX，115200、8N1**，接收端与板子共地。预期日志依次出现 `[1/4] ROM RAM initialized`、`[2/4] BLE init`、`[3/4] GAP and GATT init`、`[4/4] TMOS running`，随后进入广播和心跳。调试版还会多打一行 `VTF re-armed for diagnostics: [2]=... [3]=...`。
   **BLE 中断计数**：调试版已把 VTF 重新指向应用包装函数（见下节），所以心跳行的 `BLE中断=` 应当持续增长；若它一直为 0，说明射频中断根本没进来，优先查 MISC_CTRL、时钟源与射频参数，而不是查向量表。
3. 手机 BLE 工具扫描 **CH572-BLE-UART**，连接服务 **0xFFE0**。读取 **0xFFE1** 应返回 `11`；对 **0xFFE2** 写入再读回，验证普通 GATT 读写。
4. 在 **0xFFE4** 打开 Notify，然后向 **0xFFE3** 写入 1–20 字节，检查上行通知回显。同一连接内重复多次，再断开并重连。
5. 保持连接或广播运行至少 **3 分钟**，覆盖默认 120 秒周期校准。读取需要认证的 **0xFFE5**，让手机完成配对/绑定，断电重启后重连，检查 Flash 绑定信息仍有效。
6. 调试版通过后下载 **`build/out/ble_uart-rom-combined.hex`**，再重复广播、读写、通知和重连。发布版无串口日志，必须用手机确认行为。

示例 MAC 是演示值 C2:00:00:00:00:01，产品应分配每台设备唯一地址。示例服务的 CHAR3/CHAR4 是 BLE 回显通道，实际串口透传的业务转发需由产品应用实现。

若运行停住，记录最后一条初始化日志和任何 `mcause/mepc/mtval` 输出；若能连接但数据异常，记录具体 UUID、写入内容、通知结果和是否经过配对/校准。继续排查时使用当前 HEX 与同目录 ELF/map，避免拿旧地址反汇编。

独立应用 HEX 只适合在已有匹配 ROM 镜像时更新，下载器必须按应用扇区擦除并保留 0x1F000 的绑定信息和 0x20000 起的协议栈。更换 ROM、头文件或内存布局后，成套重编并使用合并镜像。
