# CH572 BLE 静态库 —— 架构与适配分析

本文记录「为什么 CH572 缺 BLE 静态库」「缺的到底是什么」「能补到什么程度」的完整推导过程，
所有结论都来自对两个 EVT 包里二进制的实际拆解，不是推测。

---

## 一、起点：两份 EVT 包的客观差异

比较对象：

| | CH592 | CH572 |
|---|---|---|
| EVT 包 | `CH592EVT-1.7` | `CH572EVT-1.4` |
| BLE 目录 | `EVT/EXAM/BLE/`（38 个示例） | `EVT/EXAM/BLE/`（8 个示例） |
| 静态库 | `LIB/libCH59xBLE.a` | `LIB/libCH572BLE_PERI.a` |
| 库头文件 | `LIB/CH59xBLE_LIB.h`（4637 行） | `LIB/CH572BLEPeri_LIB.h`（3675 行） |
| ROM 镜像 | `LIB/CH59xBLE_ROM.hex` / `_ROMx.hex` / `_ROM_PERI.hex` | **无** |
| 任务调度汇编 | `LIB/ble_task_scheduler.S` | **无** |

### 1.1 静态库的物理构成对比

用 `tools/ar_scan.py` 拆开两个 `.a`：

```
libCH59xBLE.a          libCH572BLE_PERI.a
  成员数 70              成员数 54
  /       37.8 KB         /       20.1 KB      （符号表）
  aes_soft.o   588 B      aes_soft.o   740 B
  memory.o    5772 B      memory.o    5528 B
  ...
  ll_master.o 21904 B     （无）
  ll_scan.o   47252 B     （无）
  ll_initiate.o 25268 B   （无）
  gap_central.o 26216 B   （无）
  central.o    8580 B     （无）
  observer.o   3708 B     （无）
  ll_whitelist.o 3800 B   （有，但符号少很多）
  ...
```

关键：**两个库有 20 多个同名对象文件**（`tmos.o`、`gap.o`、`gatt.o`、`sm.o`、`ll_connect.o`…），
说明它们出自同一套协议栈代码基线，只是编译时的**角色裁剪开关不同**。

### 1.2 符号级差异（这是最硬的证据）

用 `tools/sym_cmp.py` 与 `tools/missing_syms.py` 得到：

```
库A = libCH572BLE_PERI.a   全局定义符号 841
库B = libCH59xBLE.a        全局定义符号 1462
库A 独有:  28
库B 独有: 649          ← 这就是"缺的东西"
共有:     813          ← 这就是"能直接复用的东西"
```

**813 / 841 = 96.7% 的符号完全同名同签名。** 换句话说：
API 层面两者高度一致，一段写给 CH592 从机的代码，绝大部分可以原样编译到 CH572。

那 649 个缺失符号按模块归类如下：

| 模块 | 缺失数 | 代表符号 | 属于哪一侧 |
|---|---|---|---|
| `HCI_*` | 111 | `HCI_LE_CreateConnCmd`、`HCI_LE_SetScanParamCmd` | 主机 |
| `LL_*` | 98 | `LL_CreateConnection`、`LL_ScanEnable`、`LL_InitiateEnable` | 主机 |
| `ll_*` | 58 | `ll_scan_tx`、`ll_initiate_rx_legacy_adv`、`ll_master_process` | 主机 |
| `API_LE_*` | 45 | `API_LE_CreateConnCmd`、`API_LE_SetScanParamCmd` | 主机 |
| `rfRole*` / `RFIP_*` / `RFRole_*` | 40+ | `rfRoleBoundHostStart`、`RFIP_SetTx`、`RFRole_StartTx` | 底层射频 |
| `ATT_*` | 31 | `ATT_ReadReq`、`ATT_FindInfoReq` | GATT 客户端 |
| `gap*`（小写内部） | 30+ | `gapProcessScanningEvt`、`gapRegisterCentral` | 主机 |
| `GATT_*` | 21 | `GATT_DiscAllPrimaryServices`、`GATT_WriteCharValue` | GATT 客户端 |
| `L2CAP*`（小写内部） | 37 | `l2capSendConnectRsp`、`l2capAllocPsm` | GATT 客户端 |
| `SM_*` | 15 | `SM_InitiatorInit`、`smpInitiatorProcessIncoming` | 配对发起侧 |
| `GAPRole_Central/Observer*` | 17 | `GAPRole_CentralInit`、`GAPRole_ObserverInit` | 角色层 |
| `TMOS_*` | 7 | `TMOS_TimerIRQHandler`、`tmos_proces_idle` | 实现差异 |
| `RF_*` 跳频 | 13 | `RF_FrequencyHoppingTx`、`RF_HopGetChannel` | 2.4G 私有协议跳频 |
| 其它 | 100+ | `llAdvPeriodicAdvertising`、`llCISReq` 等 BLE 5.x 高级特性 | 高级特性 |

**规律极其清晰**：缺失的全部集中在 **主机侧（Central）+ GATT 客户端 + BLE 5.x 高级特性 + 跳频**。
从机侧（Peripheral）的 GAP / GATT Server / SM Responder / L2CAP / TMOS 全部健在。

> 而是从 API 表面就明确告知"这个芯片没有主机角色"。

## 二、为什么 CH572 做不了主机？—— 硬件约束推导

单看"库少了代码"还不够，得看**为什么**。把两颗芯片的资源摊开：

| 项目 | CH572 | CH592 | 差异倍数 |
|---|---|---|---|
| 内核 | 青稞 RISC-V3C（RV32IMBC） | 青稞 RISC-V4C（RV32IMAC） | — |
| 最高主频 | 100 MHz | 20 MHz（基本零等待） | — |
| 非易失存储 | 256 KB FlashROM | 512 KB FlashROM | 2× |
| ├ 用户程序区 | **240 KB** | **448 KB** | 1.87× |
| ├ 引导区 | 8 KB | 24 KB | — |
| └ 配置信息区 | 8 KB | 8 KB | — |
| 易失存储 SRAM | **12 KB** | **26 KB**（24K + 2K） | 2.17× |
| 电源管理 | LDO5V，无 DC-DC | 内置 DC-DC | — |
| USB | 有 | 全速主机+设备 | — |

### 2.1 没有 BLE ROM 区

CH592 的内存映射里，代码区很大：`CODE/ROM 0x0000_0000 – 0x0007_FFFF`（512 KB）。
它随包附了三个 ROM 镜像：

| 文件 | 地址范围 | 实际数据 | 用途 |
|---|---|---|---|
| `CH59xBLE_ROM.hex` | 0x0001_0000 – 0x0003_D2B8 | 184,992 字节 | 全功能协议栈固化到 ROM |
| `CH59xBLE_ROMx.hex` | 0x0004_0000 – 0x0006_D2BC | 184,996 字节 | 同上，备用地址段 |
| `CH59xBLE_ROM_PERI.hex` | 0x0000_C000 – 0x0002_D390 | 136,056 字节 | **仅从机**版本 |

配合 `ble_task_scheduler.S` 里的 `LLE_IRQHandler`，
以及链接宏 `CH59xBLE_ROM=1` —— 这是 CH592 的「方式二：固定库」开发模式：
**应用只占 0x1000 起的 44 KB，协议栈跑在 0x1_0000 以后的 ROM 里。**

再看 CH572：整个代码区只有 `0x0000_0000 – 0x0003_FFFF`（256 KB），
**没有任何 ROM 镜像，也没有 `ble_task_scheduler.S`**。

原因很简单：CH572 把"ROM"这个物理区域**当 FlashROM 用了**
（240 KB 用户区 + 8 KB 引导 + 8 KB 配置）。它没有独立的片上 ROM 存协议栈。

### 2.2 于是所有东西都得挤进 240 KB Flash + 12 KB RAM

实测数据（本工程 `libCH572BLE.a` 编译结果）：

| | 体积 |
|---|---|
| CH572 从机协议栈编译产物（`.text + .rodata`） | ≈ 89.9 KB |
| CH592 全功能协议栈编译产物 | ≈ 202.6 KB |
| 差值（被裁掉的主机侧代码） | ≈ 112.7 KB |
| CH572 应用可用 Flash | 240 KB |
| **从机方案余量** | **≈ 150 KB**（充裕） |
| 若强行加上主机侧 | 89.9 + 112.7 = 202.6 KB → 余量仅 ≈ 37 KB（且 RAM 首先不够） |

**RAM 才是真正的死穴**：CH572 只有 12 KB。
本工程实测：协议栈内存堆 5 KB + 静态 bss 1.1 KB + 栈 1.2 KB ≈ 7.3 KB，已经用掉 61%。
主机角色额外需要 scan 结果链表、initiate 状态机、多连接控制块、
白名单/解析列表缓存 —— 在只有 12 KB RAM 的芯片上根本铺不开。

**所以 WCH 的裁剪不是能力不足，是产品定位**：CH572 瞄准的是
「低引脚数的简单蓝牙应用」（数据手册原话）—— 透传模块、HID、传感器上报这类
纯从机场景，把主机能力砍掉换取成本与功耗。

## 三、那真正"能补"和"必须补"的是什么？

### 3.1 决定性发现：官方 CH572 SDK 缺 `HAL.c`

翻遍 `CH572EVT-1.4`，`EVT/EXAM/BLE/HAL/` 目录下只有：

```
HAL/include/CONFIG.h
HAL/include/HAL.h          ← 声明了 extern void CH57x_BLEInit(void);
HAL/include/KEY.h  LED.h  RTC.h  SLEEP.h
HAL/KEY.c  LED.c  RTC.c  SLEEP.c
```

**没有 `HAL.c`。** 而 `HAL.h` 里明确声明：

```c
/**
 * @brief   BLE 库初始化
 */
extern void CH57x_BLEInit(void);
```

`CONFIG.h` 里还留着一条更耐人寻味的线索：

```c
#ifdef CH57xBLE_ROM
#include "CH57xBLE_ROM.h"        /* ← 这个文件在 CH572 EVT 里不存在 */
#else
#include "CH572BLEPeri_LIB.h"
#endif
```

也就是说，CH572 的 SDK 是从 CH59x 那套工程**移植/裁剪过来的**，
移植过程中 `HAL.c` 和 `CH57xBLE_ROM.h` 这两块掉了 —— 而 `HAL.c` 恰恰是开工必需的那块。

`CH57x_BLEInit()` 要做的事情（本工程按 CH59x 官方写法 + CH572 实际符号补全）：

```c
void CH57x_BLEInit(void)
{
    bleConfig_t cfg;
    tmos_memset(&cfg, 0, sizeof(bleConfig_t));

    cfg.MEMAddr  = (uint32_t)MEM_BUF;        /* 协议栈内存堆，应用定义 */
    cfg.MEMLen   = BLE_MEMHEAP_SIZE;

    cfg.SNVAddr  = BLE_SNV_ADDR;             /* 绑定信息存 Flash 的地址 */
    cfg.SNVBlock = BLE_SNV_BLOCK;
    cfg.SNVNum   = BLE_SNV_NUM;

    cfg.BufNumber  = BLE_BUFF_NUM;           /* 收发包缓存 */
    cfg.BufMaxLen  = BLE_BUFF_MAX_LEN;
    cfg.TxNumEvent = BLE_TX_NUM_EVENT;
    cfg.RxNumEvent = BLE_BUFF_NUM;

    cfg.TxPower      = BLE_TX_POWER;         /* 射频参数 */
    cfg.WindowWidening = 2;
    cfg.WaitWindow     = 1;

    /* 6 个硬件相关回调 —— 这是 HAL 层存在的全部意义 */
    cfg.srandCB      = HAL_SrandCB;          /* 随机数种子 */
    cfg.idleCB       = HAL_IdleCB;           /* 空闲进低功耗 */
    cfg.staCB        = HAL_StaCB;            /* 异常上报 */
    cfg.readFlashCB  = HAL_FlashReadCB;      /* SNV 读 */
    cfg.writeFlashCB = HAL_FlashWriteCB;     /* SNV 写 */

    BLE_LibInit(&cfg);                       /* 启动协议栈 */
    HAL_TimeInit();                          /* 建立 RTC 时基并注册到 TMOS */
}
```

没有这份代码，`BLE_LibInit()` 永远拿不到配置，协议栈起不来，广播都发不出去。

### 3.2 结论：本工程的目标被重新定义

| 原以为要做的 | 实际该做的 |
|---|---|
| ❌ "把 CH592 的 BLE 库编译成 CH572 能用的" | ✅ **补齐官方缺失的 HAL 胶水层，并把库工程化** |
| ❌ "给 CH572 加上主机能力" | ✅ **明确告知做不到，并用能力宏在编译期拦住** |
| ❌ "逆向协议栈" | ✅ **复用官方二进制，只做重新组织与封装** |

## 四、可行性边界（明确写下来，避免返工）

| 需求 | CH572 能否做到 | 依据 |
|---|---|---|
| BLE 从机（Peripheral），被手机连接 | ✅ 可以 | `GAPRole_PeripheralInit` 等符号齐全 |
| 自定义 GATT 服务（读/写/Notify/Indicate） | ✅ 可以 | `GATTServApp_*`、`GATT_Notification` 齐全 |
| 配对绑定、Passkey、绑定信息存 Flash | ✅ 可以 | `GAPBondMgr_*`、`smResponder*`、`tmos_snv_*` 齐全 |
| 广播者（只广播不连接） | ✅ 可以 | `GAPRole_BroadcasterSetCB` 存在 |
| 连接参数更新、PHY 更新、RSSI 读取 | ✅ 可以 | `GAPRole_UpdatePHY`、`BLE_ReadRssi` 齐全 |
| 2.4G 私有协议点对点收发 | ✅ 可以 | `RF_Tx` / `RF_Rx` / `RF_SetChannel` 齐全 |
| 单连接从机 | ✅ 可以 | `PERIPHERAL_MAX_CONNECTION = 1` |
| **主动扫描 / 发起连接（Central）** | ❌ **不可以** | 缺 649 个主机侧符号，头文件亦无声明 |
| **观察者（只扫描）** | ❌ **不可以** | `GAPRole_Observer*`、`ll_scan_*` 缺失 |
| **GATT 客户端（发现/读写对端服务）** | ❌ **不可以** | `GATT_Disc*`、`ATT_ReadReq` 等缺失 |
| **多从机并发（同时被多个主机连）** | ❌ **不可以** | 缺多连接控制块相关符号，RAM 也不够 |
| **扩展广播 / 周期广播同步（BLE 5.x）** | ❌ **不可以** | `llAdvPeriodicAdvertising` 等缺失 |
| **2.4G 私有协议跳频** | ❌ **不可以** | `RF_FrequencyHopping*` 缺失 |
| **从机 + 主机共存** | ❌ **不可以** | 同 Central |

> **一句话决策规则**：你的设备是不是"被别人连"？
> 是 → CH572 没问题（而且比 CH592 便宜、引脚少）。
> 需要"主动去连别人" → 换 CH592。

## 五、本工程的适配策略

### 5.1 保持"差不多的使用方法"

设计要求是 CH572 的用法要**尽量贴近 CH592**，让开发者不必重新学一套。做法：

| CH592 的用法 | CH572 的处理 |
|---|---|
| `#include "CONFIG.h"` | ✅ 同名同位置 |
| `CH57x_BLEInit()` … 等等，CH592 叫 `CH59x_BLEInit()` | ✅ 本工程也用 `CH57x_BLEInit()`（与 CH572 官方 `HAL.h` 声明一致） |
| `GAPRole_PeripheralInit()` | ✅ **同名同签名，直接可用** |
| `GAPRole_SetParameter(GAPROLE_ADVERT_DATA, …)` | ✅ 同名，参数 ID 一致 |
| `GATTServApp_RegisterService(attrTbl, numAttrs, keySize, &cb)` | ✅ 同名同签名 |
| `uint32_t MEM_BUF[BLE_MEMHEAP_SIZE/4]` | ✅ 完全相同 |
| `TMOS_ProcessEventRegister()` / `TMOS_SystemProcess()` | ✅ 完全相同 |
| 链接 `-lCH59xBLE` | ➜ 改成 `-lCH572BLE`（本工程整理后的库） |
| `#define CH59xBLE_ROM=1`（走 ROM 模式） | ➜ **不需要**，CH572 无 ROM 模式，`ch572_ble.h` 里已自动 `#undef` |

也就是说：**从 CH592 移植一段从机代码到 CH572，通常只需要改链接的库名。**

### 5.2 新增能力探测宏（让差异显式化）

不能指望所有人记住"CH572 没有主机"，所以用宏把它写死：

```c
#define CH572_BLE_HAS_PERIPHERAL        1
#define CH572_BLE_HAS_BROADCASTER       1
#define CH572_BLE_HAS_CENTRAL           0
#define CH572_BLE_HAS_OBSERVER          0
#define CH572_BLE_HAS_GATT_CLIENT       0
#define CH572_BLE_HAS_PERIODIC_SYNC     0
#define CH572_BLE_HAS_EXT_ADV           0
#define CH572_BLE_HAS_RF_HOPPING        0
#define CH572_BLE_HAS_MULTI_PERIPHERAL  0
```

并且把不存在的 API 全部重定义成"编译期报错宏"：

```c
#if !CH572_BLE_HAS_CENTRAL
#define GAPRole_CentralInit() \
    _CH572_BLE_MISSING_API_("CH572 固件库不含主机角色 API：GAPRole_CentralInit")
...
#endif
```

技术手段是 GCC 的 `__attribute__((error("...")))`：

```c
__attribute__((error("CH572 BLE 固件库不提供该 API，请检查平台能力宏 CH572_BLE_HAS_xxx")))
void _ch572_ble_missing_api(const char *msg);
```

**效果**：误用主机 API 时，编译输出是这样的：

```
error: call to '_ch572_ble_missing_api' declared with attribute error:
       CH572 BLE 固件库不提供该 API，请检查平台能力宏 CH572_BLE_HAS_xxx
```

而不是：

```
undefined reference to `GAPRole_CentralInit'
undefined reference to `ll_initiate_tx'
undefined reference to `RFIP_SetTx'
... （还有 646 行）
```

同一个项目里两种芯片的代码可以共存：

```c
#if CH572_BLE_HAS_CENTRAL
    /* CH592 路径：主动扫描并发起连接 */
    GAPRole_CentralInit();
    GAPRole_CentralStartDevice(taskId, &bondCBs, &centralCBs);
#else
    /* CH572 路径：老老实实做从机 */
    GAPRole_PeripheralInit();
#endif
```

### 5.3 构建系统：不依赖 MounRiver 也能验证

MounRiver Studio 的工程文件（`.cproject`）是 Eclipse CDT 的 XML，难以在 CI 里跑。
本工程提供两条并行路径：

1. **`scripts/build.ps1`**（主路径）：纯命令行，自动探测工具链，
   完成「编译 HAL → 解包官方库 → 重新打包 → 编译示例 → 链接 → 生成 hex → 体积统计 → 指令集自检」全流程。
2. **`scripts/make_mrs_project.ps1`**（给 IDE 用户）：
   以官方 `Peripheral` 示例的 `.cproject` 为模板，用字符串定位法精确替换 6 个 option
   （头文件路径 / 汇编头文件路径 / 库路径 / 库名 / 链接脚本 / 宏定义），
   生成可直接被 MRS 导入的工程。

路径用 `PARENT-2-PROJECT_LOC`（相对于 `examples/<示例名>/` 往上两级），
因此**整个 `CH572_BLE_LIB` 目录可以随意拷贝到任何路径，工程依然有效**。

### 5.4 指令集兼容性自检（这是本次踩到的真坑）

因为当前环境里没有 MounRiver 自带的 `riscv-none-embed-gcc`，
本工程用 MounRiver Studio 2 自带的 WCH 定制工具链
`riscv-wch-elf-gcc`（GCC 12.2）做正式构建；并额外用 ESP-IDF 的
`riscv32-esp-elf-gcc`（GCC 14.2）交叉验证过一遍，确认工程不依赖特定工具链。
这带来两个必须处理的问题：

**问题 1：`mcpy` 是沁恒自定义指令，通用工具链不认**

`core_riscv.h` 里：

```c
__attribute__((always_inline)) RV_STATIC_INLINE void __MCPY(void *dst, void *start, void *end)
{
    __asm volatile("mcpy %2, %0, %1" : "+r"(start), "+r"(dst) : "r"(end) : "memory");
}
```

通用工具链报：`Error: unrecognized opcode 'mcpy a2,a1,a5'`。

该函数只被 `CH57x_sys.c` 的 `__wrap_memcpy()` 使用一次，而本工程并没有启用
`-Wl,--wrap=memcpy`，所以它实际不会被调用到，但**必须能编译过**。
处理：在 `core_riscv.h` 里加条件分支，定义 `USE_STD_MCPY` 时退化为标准逐字节拷贝。
构建脚本检测到非 WCH 工具链时自动加上这个宏。

**问题 2：中断属性 `WCH-Interrupt-fast` 是沁恒扩展**

`CH57x_common.h` 里：

```c
#ifdef INT_SOFT
#define __INTERRUPT   __attribute__((interrupt()))
#else
#define __INTERRUPT   __attribute__((interrupt("WCH-Interrupt-fast")))
#endif
```

通用工具链只给个 warning。构建脚本对非 WCH 工具链自动加 `-DINT_SOFT` 降级。

**问题 3：CH572 是 RV32IMBC，没有 A 扩展（原子指令）也没有浮点**

用 `rv32imac` 编译理论上可能生成 `amo*` / `lr.w` / `sc.w` 原子指令，
这些指令在 CH572 上会触发非法指令异常直接跑飞。
所以本工程附带 `tools/isa_check.py`：

1. 从 ELF 符号表取出全部 `STT_FUNC` 符号，按地址排序；
2. **只对真实函数区间**线性扫描解码（避免把 `.text` 里的字符串/跳转表当指令，
   产生大量假阳性 —— 所以必须先取函数符号再解码）；
3. 按 RISC-V 规范判断 opcode 归属，报告 A 扩展 / 浮点 / 未知 opcode。

构建流程最后自动调用它。实测结果：

```
函数符号: 676 个（只扫描这些真实代码区间）
解码指令数: 28998

  compressed(16bit)           18622
  op-imm                       2643
  branch                       1347
  load                         1337
  jal                          1274
  store                        1183
  op                           1055
  auipc                         814
  jalr                          360
  lui                           257
  fence                          72
  system                         34

  [通过] 无 A 扩展原子指令、无浮点指令。
  [通过] 无标准 RISC-V 之外的 opcode。
结论: [通过] 产物指令集与 CH572 兼容
```

> 顺带一提：`fence` 72 条来自 `SAFEOPERATE asm volatile("fence.i")`（Flash 操作后的指令缓存同步），
> `system` 34 条来自 `PFIC_*` 中断控制里的 `csrrs/csrrc`。都属于正常使用。

### 5.4.1 用 WCH 官方工具链就没有这两个问题了

以上三个问题（`mcpy`、`WCH-Interrupt-fast`、A 扩展指令）都是
**通用工具链**才会遇到的。换成 MounRiver Studio 2 自带的
`riscv-wch-elf-gcc`（GCC 12.2）后：

- `mcpy` 直接汇编通过，实测产物里真的生成了 3 处 `mcpy` 指令；
- `WCH-Interrupt-fast` 生效，中断函数用青稞内核的硬件压栈，
  `RTC_IRQHandler` 的汇编里 `mret` 之前**没有任何寄存器保存代码**；
- 不需要 `-DINT_SOFT` / `-DUSE_STD_MCPY` 这两个降级宏。

构建脚本会自动判断工具链来源：是 WCH 家的（`riscv-none-*` / `riscv-wch-elf*`）
就不加降级宏，是通用的就自动加上。所以两条路都能走通。

**实测体积差异**：

| | 通用工具链（ESP-IDF GCC 14.2） | WCH 工具链（GCC 12.2） |
|---|---|---|
| ROM 镜像 bin | 89,900 字节 | **89,316 字节** |
| 应用 text（ROM 方式） | 6,360 字节 | **6,140 字节** |
| 可用栈 | 1,232 字节 | **1,384 字节** |

### 5.5 RAM 调优（CH572 上最紧张的资源）

第一次编译用 `BLE_MEMHEAP_SIZE = 6144`（官方建议的 6K 下限），实测：

```
0x200012B0  _sbss
0x20002F30  _ebss        → bss = 7296 字节
0x20003000  _eusrstack   → 栈空间 = 4096 - 7296 + ... ≈ 224 字节  ← 太紧！
```

栈只剩 224 字节，一次深一点的调用链就会踩坏 bss。调整到 `512*10 = 5120` 后：

```
0x200012B0  _sbss
0x20002B30  _ebss        → bss = 6272 字节
0x20003000  _eusrstack   → 栈空间 ≈ 1232 字节  ← 健康
```

功能验证：广播、连接、GATT 读写、Notify、配对绑定全部正常。
所以本工程默认 `BLE_MEMHEAP_SIZE = 512*10`，并在头文件里写清了权衡方法。

## 六、如果一定要 CH572 做主从一体，有出路吗？

诚实的回答：**本工程做不到，且不建议尝试**。列一下如果要硬做需要什么：

1. **拿到协议栈源码**：WCH 未公开 BLE 协议栈 C 源码；
2. **拿到 CH572 的 ROM dump**：CH572 根本没有 BLE ROM 区可 dump；
3. **拿到 CH592 的 ROM 镜像直接搬家**：CH592 的 ROM 镜像链接地址是 `0x1_0000`，
   而 CH572 的 Flash 最高只到 `0x3_FFFF`；且两者内核不同
   （V3C vs V4C）、射频寄存器布局不同、中断控制器不同 —— **不可移植**；
4. **反向工程 CH572 的 `libCH572BLE_PERI.a`**：即使把协议栈反汇编改出来，
   还要处理 RAM 布局（12 KB 装不下主从双角色状态机）、
   射频时隙调度（单射频收发器在扫描/连接/广播之间切换需要精确计时）等；
   工作量远大于直接换 CH592，且风险极高。

**正确做法**：
- 需要主从一体 → 用 **CH592**（26 KB RAM / 448 KB Flash / 有 BLE ROM）；
- 只需要从机 → 用 **CH572**（成本与引脚优势明显），配本工程的库。

## 七、本次分析用到的工具（都在 `tools/` 下，可复现）
