# 最终结论：ROM 方式在 CH572 上不可行

> 本文是**结论性文档**。基于上板实测 + 完整数据核算。
> 相关：[`../MEMORY.md`](../MEMORY.md)、[`交接文档.md`](交接文档.md)

---

## 一、决定性证据

同一块 CH572D-R0-1V1、同一份应用代码，只换固件：

| 固件 | 结果 |
|---|---|
| **静态库方式** | ✅ 协议栈初始化正常，**手机能搜到设备** |
| ROM 方式 | ❌ 协议栈初始化全过、广播日志正常，**射频不工作、搜不到** |

这个对照实验把问题范围压到了"ROM 方式特有的差异"上。

## 二、根本原因：RAM 不够

### 两种方式的 RAM 需求核算

```
【静态库方式】—— 实测可用 ✓
  .highcode（必须在 RAM 执行） :   4044
  .data                        :    596
  .bss                         :   6272
  ------------------------------------
  合计                         :  10912  (10.66 KB)
  剩余给栈                     :   1376       ← 刚好够

【ROM 方式】—— 实测不可行 ✗
  ROM 镜像 .highcode（必须在 RAM）:  10496   ← 协议栈热路径/中断处理
  ROM 镜像 .data                  :     68
  ROM 镜像 .bss                   :   1136
  应用 .data                      :    484
  应用 .bss                       :   5276
  ------------------------------------
  合计                            :  17460  (17.05 KB)
  RAM 总量                        :  12288  (12.00 KB)
  缺口                            :   5172  (5.05 KB)  ★
```

### 为什么 ROM 的 `.highcode` 必须进 RAM

预编译的协议栈库（`libCH572BLE_PERI.a`）里，一批函数标了 `.highcode` 段，
它们的**运行期地址是写死的 RAM 绝对地址**（实测 `0x20000600 - 0x200012FE`）。

- **静态库方式能工作**：应用的 startup 把 `.highcode` 从 Flash 搬到 RAM
  （实测搬运 4044 字节 → `0x20000000-0x20000FCC`），那些绝对地址上真的有代码。

- **ROM 方式失效**：这段代码留在 ROM 镜像的 Flash 里（`0x33xxx`），
  而 RAM 里对应地址是**空的**。协议栈里的调用形如 `jalr → 0x2000xxxx`，
  跳过去就是空白 —— 射频中断处理、Flash 操作全部失效。

这正好解释了那个现象：**初始化路径上的 `tmos_*` 等函数恰好不在 `.highcode` 里
（能在 Flash 跑），所以 9 步初始化全过；一旦真正收发数据，就踩到必须位于 RAM 的函数上。**

### 为什么 ROM 的 `.highcode` 比静态库的大一倍多

ROM 链接为保证跳转表里**每个** API 都有确定地址，**必须关闭 `--gc-sections`**
（开了会把"当前没人调用"的函数裁掉，跳转表项指向空地址）。
关掉之后 `.highcode` 里就保留了全部带该段属性的函数。

| | `.highcode` 大小 |
|---|---|
| 静态库方式（开 gc） | 4,044 字节 |
| ROM 方式（关 gc） | **10,496 字节** |

## 三、排查过程中修掉的真问题（都已修复，对静态库方式同样有价值）

虽然最终结论是 ROM 方式不可行，但排查过程中定位并修复了一批**真实缺陷**：

| # | 问题 | 影响范围 |
|---|---|---|
| 1 | `R32_MISC_CTRL` 射频位未配置 | 两种方式（**射频完全不工作**） |
| 2 | ROM 版本串与 `VER_FILE` 不一致 | ROM 方式 |
| 3 | `SysTick_Handler` 落到启动文件死循环 | 两种方式（~43 秒后卡死） |
| 4 | 启动文件误用 `EXAM\SRC` 变体（`mstatus=0x88`，MPP=用户模式） | 两种方式 |
| 5 | 链接脚本 `FLASH_ROM_END` 与 ISP 库函数重名 | ROM 方式 |
| 6 | ROM 的 `.data/.bss` 无人初始化 + 应用 RAM 覆盖 | ROM 方式 |
| 7 | BLE 中断向量悬空（弱符号未解析到强定义） | ROM 方式 |
| 8 | 出厂 MAC 为全 0（`0x3F018` 读出 `00 00 00 00`） | 两种方式（手机忽略无效地址） |

**其中 #1、#3、#4、#8 对静态库方式是必须的** —— 也就是说，
静态库方式之所以现在能正常工作，依赖的正是这些修复。

## 四、建议

### 用静态库方式（已验证可用）

| 项目 | 数值 |
|---|---|
| 固件 | `build/out/ble_uart.hex` |
| 烧录地址 | `0x00000000`（**只需一个文件**） |
| RAM 占用 | 10,912 字节（剩 1,376 给栈） |
| Flash 占用 | ~87 KB（可用 240 KB） |
| 应用代码 | 与 ROM 方式**完全相同**，只换编译宏与链接库 |

### 如果一定要 ROM 方式

只有两条路，都超出本工程范围：

1. **让 WCH 提供 CH572 专用的 ROM 库**（像 CH59x 那样）。
   CH59x 能做 ROM 方式是因为它有 26 KB RAM、448 KB Flash；
   CH572 只有 12 KB RAM，装不下。
2. **拿到重新编译的协议栈库**：要求用 `-ffunction-sections` 编译，
   且 `.highcode` 段只放真正必须在 RAM 的函数（如 ISP 的 Flash 操作），
   协议栈热路径可以留 Flash 执行（性能略降，但功能可用）。

   粗估：若 `.highcode` 能压到 2 KB 以内，ROM 方式即可行
   （ROM 变量 1.2 KB + highcode 2 KB + 应用 5.8 KB ≈ 9 KB < 12 KB）。

## 六、给后续接手人的提醒

1. **不要再尝试把 ROM 方式搬到 CH572** —— 除非拿到更小的 `.highcode` 库。
   本文有完整实测数据，不是估算。

2. **`.highcode` 必须能进 RAM** 这条规律对两种方式都成立，
   是 WCH 芯片 Flash 操作与射频时序的基本要求。

3. **ROM 与应用是两个独立链接的镜像**，中间所有接缝都要显式对齐 ——
   不能指望"同名符号自动接上"。排查中 #5、#6、#7 都是这个根源的变体。
