# 实机排查指南：搜不到蓝牙信号怎么办

> 本文是**上板调试手册**。按顺序做完，能定位到具体是硬件、时钟、启动还是协议栈的问题。
>
> 相关：[`交接文档.md`](交接文档.md)、[`../MEMORY.md`](../MEMORY.md)

---

## 零、先确认一件事：你烧的是修复后的固件吗

**2026-10-08 修复了一批 HAL 初始化遗漏**（详见 [`交接文档.md` 第 9.5 节](交接文档.md#95-hal-初始化实机搜不到信号的那次)）。
修复前的固件**射频完全不工作** —— 因为 `R32_MISC_CTRL` 的 bit24-29 没有配置。

修复后必须**两个 hex 都重新烧**（ROM 里新增了导出入口，大小变了）：

| 文件 | 烧到 | 当前大小 |
|---|---|---|
| `lib/CH572BLE_ROM.hex` | `0x00020000` | 251,334 字节（数据 89,324） |
| `build/out/ble_uart-rom.hex` | `0x00000000` | 19,524 字节 |

> **只烧应用不烧 ROM 是常见错误** —— ROM 变了就必须重烧。

## 一、用调试版固件看程序跑到哪（最重要的一步）

发布版固件的串口**不会有任何输出**：`PRINT` 宏在 `CH57x_common.h` 里是
`#ifdef DEBUG` 才展开成 `printf` 的，默认是空宏；`printf` 底层的 `_write`
也被同样条件包着。

所以要排查，先换成**调试版**：

```powershell
cd CH572_BLE_LIB
powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Target all -DebugBuild
```

生成 `build\out\ble_uart-rom.hex`（调试版约 42 KB）。
或者直接用已经生成好的：`build\out\ble_uart-rom-调试版.hex`

**调试版会额外做三件事**：
1. 初始化 UART（**PA3 = TX，PA2 = RX，115200 8N1**）
2. 在 `main()` 最开始把 **PA5 拉高**（判断程序有没有跑到 main）
3. 打印时钟实测值 + 6 步初始化进度

### 1.1 接线

```
CH572 板          USB-TTL
  PA3 (TX)  ────→  RXD
  PA2 (RX)  ←────  TXD
  GND       ─────  GND
```

> 如果你用的是 EVT 板自带的 CH340 USB 口，一般就是 PA3/PA2 直连，直接插 USB 即可。
> **注意：不要同时接两路串口**，会打架。

### 1.2 期望看到的输出（正常情况）

```
===== CH572 BLE ROM 方式调试信息 =====
ROM 版本      : CH572_BLE_ROM_V1.0
期望系统时钟  : 100000000 Hz (100MHz)
实测系统时钟  : 100000000 Hz
时钟偏差      : 0 Hz
时钟判断      : 正常（32MHz 晶振已起振）
======================================

[1/6] 时钟与串口就绪
[2/6] ROM 中断钩子已注册
[3/6] 正在初始化 BLE 协议栈（CH57x_BLEInit）...
[4/6] 协议栈初始化完成
[5/6] HAL 初始化完成
[6/6] 正在启动 GAP 从机角色与 GATT 服务...

全部初始化完成，开始广播。
  设备名  : CH572-BLE-UART
  服务 UUID: 0xFFE0
```

看到最后一句就说明软件侧没问题，搜不到就是**硬件/射频**问题（跳到第三节）。

## 二、根据输出定位问题

### 情况 1：串口完全没有输出，但 PA5 测不到高电平

**结论：程序根本没跑到 `main()`。** 问题在启动阶段（在时钟配置之前就挂了）。

可能原因：
- **Flash 烧录地址不对** —— 应用必须烧到 `0x00000000`，ROM 镜像必须烧到 `0x00020000`。
  用 WCHISPTool 打开 hex 时确认它识别出的地址范围：
  - 应用 hex 应显示 `0x00000000 - 0x00001A14` 左右
  - ROM hex 应显示 `0x00020000 - 0x00035CEC` 左右
- **烧录不完整** —— 重新擦除整片再烧。
- **芯片没正常工作** —— 检查供电（3.3V）、复位引脚、晶振。

### 情况 2：串口没有输出，但 PA5 测到高电平

**结论：`main()` 执行了，但串口没配好或时钟不对。**

PA5 变高说明 `Debug_EarlyGpioHint()` 执行了 —— 那是 `main()` 的第一条语句。
所以程序在跑，问题出在后面的时钟配置或串口。

可能原因：
- 时钟配置挂住（`SetSysClock` 等 PLL 锁定超时）→ 后面的串口初始化没执行
- UART 引脚被占用 / 接错
- 波特率不对（下面第 3 种情况）

### 情况 3：串口有输出但是**乱码**

**结论：系统时钟不对 —— 大概率 32 MHz 晶振没起振。**

`UART_BaudRateCfg()` 是用 `GetSysClock()` 算分频的：

```c
x = 10 * GetSysClock() / 8 / baudrate;
x = (x + 5) / 10;
R16_UART_DL = (uint16_t)x;
```

所以时钟一错，波特率就跟着错，输出就是乱码。

**代码走的时钟路径**：
```c
HSECFG_Capacitance(HSECap_18p);            // 按 18pF 负载电容配
SetSysClock(CLK_SOURCE_HSE_PLL_100MHz);    // 外部 32MHz 晶振 → PLL → 100MHz
```

**必须检查的硬件**：
1. 板子上**有没有 32 MHz 晶振**（不是 32.768 kHz 那个 RTC 晶振）
2. 晶振有没有焊好、虚焊
3. **负载电容是否匹配** —— 代码按 `HSECap_18p` 配置，
   如果板子实际用的是别的电容值，需要改这一行（可选 `HSECap_10p` ~ `HSECap_22p`）
4. 有没有起振（示波器看晶振引脚，应有 32 MHz 正弦波）

> **提示**：也可以试试把晶振配置换成内部 RC 来验证是不是晶振问题：
> `SetSysClock(CLK_SOURCE_HSI_PLL_100MHz)`（如果 SDK 提供这个选项）。
> 内部 RC 精度不够跑 BLE，但能用来区分"是晶振问题"还是"其他问题"。

### 情况 4：打印停在 `[3/6] 正在初始化 BLE 协议栈...`

**结论：`CH57x_BLEInit()` 卡住了。** 分几种：

| 卡在哪 | 说明 |
|---|---|
| `head file error...` | 头文件版本与 ROM 里的版本串不匹配。**检查 ROM 镜像是不是最新的**（重新烧） |
| `SNV config error...` | SNV 地址配置越界（`BLE_SNV_ADDR + 256 > 0x40000`） |
| `MEM_BUF 配置错误` | 堆地址为空或小于 3 KB |
| `LIB init error code: xx` | 协议栈初始化失败，**把 xx 这个错误码记下来告诉我** |
| 没有任何错误信息就停住 | MAC 地址读取（`GetMACAddress`）卡住，或内部死循环 |

### 情况 5：打印到 `[6/6]` 但没有任何"全部初始化完成"

**结论：GAP 角色或 GATT 服务注册失败。** 这一般是 RAM 不够（协议栈堆太小）
或者服务定义有问题。

## 二点五、实战记录：已经定位并修复的两个问题

### 问题 1：串口完全无输出（已修复）

**原因**：PRINT 宏是 #ifdef DEBUG 才展开成 printf 的，默认空宏；
printf 底层的 _write 也被同样条件包着。发布版固件本来就不打印。

**修复**：加了 -DebugBuild 开关与调试版固件（见第一节）。

### 问题 2：head file error 卡在 [3/6]（已修复）

**现象**：
`
[3/6] 正在初始化 BLE 协议栈（CH57x_BLEInit）...
head file error... 库版本与头文件不匹配
`

**原因**：ROM 里的 VER_LIB 与头文件的 VER_FILE 不一致。
协议栈启动时会做校验 	mos_memcmp(VER_LIB, VER_FILE, tmos_strlen(VER_FILE))，
不一致就停在 while(1)。

- ROM 原先写的：CH572_BLE_ROM_V1.0（自定义名字）
- 头文件期望的：CH572_BLE_PERI_LIB_V1.3（协议栈真实版本）

**修复**：构建时自动从协议栈头文件读取 VER_FILE，生成 
om/rom_version.h。
详见 MEMORY.md 第十六节。

**这类问题的识别特征**：卡在 [3/6] 并打印 head file error。
如果以后还会出现，检查 ROM 与头文件是否都是最新生成的那一份。

> 注意：**ROM 镜像里的版本串不是随便起的名字**，它参与协议栈的启动校验。

## 三、如果调试输出显示一切正常，但手机还是搜不到

那就转到**射频/硬件**方向：

### 3.1 天线

- 板子上有没有天线（PCB 天线 / 陶瓷天线 / 外接）
- `蓝牙芯片的电路及PCB设计的重要注意事项.pdf`（在 `CH572EVT-1.4/EVT/PUB/`）
  里讲了 RF 走线要求 —— 可以对照检查
- 发射功率默认 0 dBm（`LL_TX_PWR_0_DBM`），可以试着调高：
  ```c
  -Defines BLE_TX_POWER=LL_TX_PWR_4_DBM
  ```
  （具体可选值见 `CH572BLEPeri_LIB.h` 里的 `LL_TX_PWR_*`）

### 3.2 用官方示例做交叉验证（**强烈建议**）

这是区分"我的适配有问题"和"板子/环境有问题"最有效的办法：

1. 用 MounRiver Studio 打开官方例程
   `CH572EVT-1.4\EVT\EXAM\BLE\Peripheral`
2. 编译烧录（**只烧官方这一个固件，不要烧我的 ROM 镜像**）
3. 用手机搜 —— 官方例程的设备名应该能搜到

| 官方例程的结果 | 结论 |
|---|---|
| 能搜到 | 板子和环境没问题，**是我的适配有问题** —— 请把调试输出发我 |
| 搜不到 | 板子/硬件/烧录流程有问题 —— 先解决这个 |

> 官方 `Peripheral` 例程用的是**静态库方式**（协议栈编进固件），
> 不依赖我的 ROM 镜像，所以能干净地隔离变量。

### 3.3 RF 直连测试（如果板子支持）

`CH572EVT-1.4\EVT\EXAM\RF\Direct_Test_Mode` 是 DTM 测试例程，
配合 WCH 的 RF 测试工具可以在不跑协议栈的情况下测射频 ——
能直接判断射频硬件是否正常。

## 四、把结果反馈给我时需要提供

为了能继续定位，请提供：

1. **PA5 的电平**（用万用表测，或接 LED）
2. **调试版的完整串口输出**（从复位开始，包括乱码部分）
3. **串口参数**（波特率、数据位、停止位、校验）—— 应该是 115200 8N1
4. **烧录工具和地址** —— 用 WCHISPTool 还是 MRS？应用烧到 `0x0`、ROM 烧到 `0x20000` 确认了吗？
5. **官方例程能否搜到**（第 3.2 节）
6. **板子照片或原理图**（尤其是晶振和天线部分）

## 五、已经排除的问题（避免重复排查）

以下是已经验证过、**不是**原因的项目：

| 项目 | 验证方式 | 结论 |
|---|---|---|
| 启动地址 | 所有官方示例的链接脚本都是 `ORIGIN = 0x0` | 硬件从 `0x0` 启动，我的布局正确 |
| 启动代码 | 与官方 `startup_CH572.S` 逐段对比 | 一致（`.highcode` 拷贝、bss 清零、`mtvec`/`mepc` 设置） |
| ROM 镜像结构 | `rom_inspect.py` 检查魔数/UUID表/跳转表 | 符合 WCH 约定，0 项越界 |
| 跳转表地址 | `rom_verify.py` 逐项核对 94 个 API | 0 项不匹配 |
| 指令集兼容性 | `isa_check.py` 反汇编 3 个 ELF | 无原子指令、无浮点指令 |
| HAL 初始化顺序 | 与官方 `MCU.c` 逐行对比 | 一致（已修复 4 项遗漏） |
| MISC_CTRL 射频位 | 反汇编确认 `0x40001048` 读改写 | 已确认写入 bit24-29=0x0E |
| SysTick 配置 | 反汇编确认 `0xE000F004/8/C` | 已确认 |
| PFIC 中断优先级 | 反汇编确认写 `0xE000E415`（IPRIOR[21]） | 已确认 |
| 版本一致性检查 | 反汇编确认 `tmos_memcmp` 调用 | 已确认 |
| SNV 地址不撞 ROM | `run_tests.ps1` 4b-2 节自动检查 | 通过（SNV `0x1F000`，ROM `0x20000`） |

**这些都已经用工具验证过，不用再查了。**
