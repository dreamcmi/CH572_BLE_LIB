2. 架构分层：这套东西到底提供了什么

从下往上看就是软件栈。橙色是本工程补的 HAL 层， 紫色是 ROM 方式特有的部分。

方式 A 静态库：协议栈编进应用固件

应用层 examples/ble_uart/src/*.c
GAP 角色层 / GATT 服务层 GAPRole_Peripheral* · GATTServApp_*
HAL 硬件抽象层　本工程新增 hal/HAL.c · include/ch572_ble.h
BLE 协议栈（二进制，编译进应用） lib/libCH572BLE.a（≈80 KB 进应用固件）
标准外设驱动 + 启动 + 链接脚本 src/StdPeriphDriver/ · src/Startup/ · src/Ld/Link.ld

方式 B ROM 镜像：协议栈固化在 Flash 固定段

应用层（只剩业务逻辑，6 KB） examples/ble_uart/src/main_rom.c 等
GAP 角色层 / GATT 服务层 同上，但 API 变成对 ROM 绝对地址的调用
HAL 层　本工程新增 hal/HAL.c（留在应用里，负责启动协议栈 + 注册中断钩子）
ROM 镜像边界　固定地址 CH572BLE_ROM.h：API → BLE_LIB_JT(n) 宏
BLE 协议栈 ROM 镜像（88 KB，烧一次不动） lib/CH572BLE_ROM.hex @ 0x00020000
CH572 硬件　RISC-V3C · 240KB Flash · 12KB RAM —
为什么必须补 HAL 层？
WCH 的 CH572 SDK 里只有 HAL.h（声明了 CH57x_BLEInit()）， 却没有 HAL.c。协议栈二进制通过 bleConfig_t 结构体接收配置和 6 个硬件回调，而"填结构体、注册回调、调用 BLE_LibInit()" 这套胶水代码必须由用户自己写 —— 官方漏给了。 连 CONFIG.h 里都还留着 #include "CH57xBLE_ROM.h" （该文件在 CH572 EVT 里并不存在）的分支，说明这套 SDK 是从 CH59x 移植裁剪过来的。

3. ROM 镜像的内存布局

镜像内部（严格对齐 WCH 官方约定）

ROM_BASE = 0x00020000（可改）

ROM_BASE + 0x00    8 字节     镜像标识
                              +0x00  uint32 魔数 0x43483537（"CH57"，小端）
                              +0x04  uint32 保留
ROM_BASE + 0x08   44 字节     UUID 表（22 项 × 2 字节，小端 GATT UUID）
ROM_BASE + 0x34  156×4 字节   函数跳转表
之后                          版本字符串 "CH572_BLE_ROM_V1.0"
之后                          代码 + 只读数据

总计：89,316 字节（87.2 KB），地址范围 0x00020000 - 0x00035CE3
这个布局不是猜的
是从官方 CH59xBLE_ROM_PERI.hex 反解出来的： 用 tools/rom_inspect.py 可以清楚看到它的 +0x08 是 UUID 表（0x1800 / 0x1801 / 0x2800 ...，与官方头文件下标一一对应）、 +0x34 是函数跳转表、JT(0) 指向版本字符串。 本工程完全照搬这套约定，所以应用侧用法与 CH59xBLE_ROM.h 一致。

Flash 分区（ROM 方式）

CH572 用户 Flash = 240 KB = 0x00000 - 0x3BFFF

0x00000000 - 0x0001EFFF  124 KB   app 主体（连续一整块）← 只更新这一块
0x0001F000 - 0x0001FFFF    4 KB   SNV 绑定信息存储区（运行期写，不烧录）
0x00020000 - 0x00035CE3  ~88 KB   BLE 协议栈 ROM 镜像 ← 先烧一次，不再改动
0x00035CE4 - 0x0003BFFF  ~25 KB   余量（ROM 将来长大了可往后扩）
0x0003C000 - 0x0003FFFF   16 KB   芯片固定占用（BootLoader + INFO）

分区在两边都有强制保证，不是靠人记：

  • ROM 侧：rom/rom_link.ld 里 LENGTH = 208K，超了链接失败
  • 应用侧：src/Ld/Link_rom.ld 里 FLASH_ROM_END = 0x1F000（= ROM 基址 0x20000 − SNV 4 KB）
  • 头部布局：链接脚本用 ASSERT 断言 .rom_header 必须正好 0x34 字节

4. 运行流程（设备端上电到收发数据）

1
硬件复位 → 启动文件
src/Startup/startup_CH572.S 的 _start 执行： 关全局中断 → 清 bss → 把 .highcode 从 Flash 搬到 RAM （CH572 的高速代码段必须跑在 RAM）→ 初始化栈指针 → 跳 main()
2
配置系统时钟
R16_PIN_ALTERNATE &= ~RB_PIN_DEBUG_EN;   // 关两线调试口
HSECFG_Capacitance(HSECap_18p);           // 32MHz 晶振负载电容
SetSysClock(CLK_SOURCE_HSE_PLL_100MHz);   // PLL 到 100MHz
BLE 协议栈要求 HSE 必须是 32 MHz。 晶振不起振 → 射频不工作 → 手机搜不到设备，这是最常见的翻车点。
3
装 ROM 中断钩子　仅 ROM 方式　必须做
ROM 方式最容易漏的一步
BLE 的基带中断（BB）与链路层中断（LLE）处理函数在 ROM 里。 应用的启动文件里这两个中断是"弱定义 + 死循环"， 不接管的话射频中断一触发就停在死循环 —— 表现为"能广播但一连接就死"或者"完全连不上"。 
static rom_app_hooks_t hooks = { .magic = ROM_HOOK_MAGIC };

const rom_handles_t *h = CH572BLE_ROM_GetHandles();  // 取 ROM 中断入口
hooks.ble_irq_handler = h->bb_irq;    // 基带中断 → ROM 实现
hooks.lle_irq_handler = h->lle_irq;   // 链路层中断 → ROM 实现
hooks.rtc_irq_handler = RTC_IRQHandler; // RTC 由应用处理

CH572BLE_ROM_Init(&hooks);            // 注册给 ROM，同时取版本号
官方 CH59x 是把这几个入口写到 RAM 固定地址 0x20000000 + n*4，应用再去读。 本工程改成 ROM 导出一个取地址函数：省 12 字节 RAM，也不依赖地址约定。
4
CH57x_BLEInit() —— 启动协议栈　本工程补全的关键函数
bleConfig_t cfg;
tmos_memset(&cfg, 0, sizeof(cfg));

cfg.MEMAddr = (uint32_t)MEM_BUF;   // 协议栈内存堆（应用定义的 5 KB）
cfg.MEMLen  = BLE_MEMHEAP_SIZE;
cfg.SNVAddr = BLE_SNV_ADDR;        // 绑定信息存 Flash 的地址
cfg.BufNumber = 3;  cfg.BufMaxLen = 27;   // 收发缓存
cfg.TxPower  = LL_TX_PWR_0_DBM;

// ★ 6 个硬件回调 —— HAL 层存在的全部意义
cfg.srandCB      = HAL_SrandCB;       // 随机数种子
cfg.idleCB       = HAL_IdleCB;        // 空闲进低功耗
cfg.staCB        = HAL_StaCB;         // 异常上报
cfg.readFlashCB  = HAL_FlashReadCB;   // SNV 读
cfg.writeFlashCB = HAL_FlashWriteCB;  // SNV 写（含擦除）

BLE_LibInit(&cfg);                    // 协议栈开始运行
HAL_TimeInit();                       // 建 RTC 时基并注册到 TMOS
ROM 方式下协议栈的代码在 ROM，但它的数据（内存池、 各种控制块）仍在 RAM，所以 MEM_BUF 一样要由应用提供。
5
HAL_Init() + GAPRole_PeripheralInit()
HAL_Init() 注册 HAL 的 TMOS 任务并启动周期校准事件。
GAPRole_PeripheralInit() 初始化从机角色。
6
应用初始化：配置广播 + 注册 GATT 服务
BLE_UART_Init();
  ├─ TMOS_ProcessEventRegister(BLE_UART_ProcessEvent)   // 注册自己的任务
  ├─ GAPRole_SetParameter(GAPROLE_ADVERT_DATA,  …)      // 广播数据
  ├─ GAPRole_SetParameter(GAPROLE_SCAN_RSP_DATA, …)     // 扫描响应（放设备名）
  ├─ GAPRole_SetParameter(GAPROLE_ADVERT_ENABLED, TRUE) // 使能广播
  ├─ GAP_SetParamValue(TGAP_DISC_ADV_INT_MIN/MAX, 160)  // 广播间隔 100ms
  ├─ GAPBondMgr_SetParameter(…配对参数…)
  ├─ GGS_AddService()          // GAP 服务
  ├─ GATTServApp_AddService()  // GATT 服务
  ├─ BLE_UART_AddService()     // ★ 自定义 0xFFE0 服务
  └─ tmos_set_event(taskID, BLE_UART_START_DEVICE_EVT)
7
进入 TMOS 主循环 —— 开始广播
while(1)
{
    TMOS_SystemProcess();     // ★ 所有 BLE 事件都在这里被处理
}
ROM 方式下 TMOS_SystemProcess 是一个宏，展开成对 ROM 里调度器的间接调用。

主循环里绝对不能写阻塞代码（delay、死等串口等）， 否则会错过连接事件时序，表现为"连不上"或"连上就掉"。 需要延时请用 tmos_start_task() 注册 TMOS 定时事件。
8
手机连接 → 状态回调被触发
bleUartStateCB() 收到 GAPROLE_CONNECTED： 
bleUartConnHandle = pLink->connectionHandle;
BLE_UART_OnLinkEstablished(bleUartConnHandle);   // 通知服务层可以发通知了
tmos_start_task(taskID, BLE_UART_PERIODIC_EVT, …);
tmos_set_event(taskID, BLE_UART_PARAM_UPDATE_EVT);  // 请求更合适的连接参数
9
断开连接 → 复位状态 → 重新广播
连接句柄复位，linkDB 回调里 GATTServApp_InitCharCfg() 复位 CCC， 然后自动回到广播状态等待下一次连接。
为什么必须复位 CCC？
CCC（客户端特征配置）记录着"手机是否使能了 Notify"。 不复位的话下次连接会残留上一次的使能状态， 导致设备在手机还没订阅时就尝试发通知 → 发送失败或行为异常。

5. 数据流：手机 ↔ CH572 一次收发经过哪些层

下行：手机 → CH572（写特征值 0xFFE3）

手机 App
  │  ATT Write Request
  ▼
[ 射频 ] ─► [ 链路层 LL ] ─► [ L2CAP ]
                                │
                                ▼
                           [ ATT Server ]
                                │
                                ▼
                     [ GATT Server 分发 ]
                                │
                                ▼
      bleUart_WriteAttrCB()  ◄──┘
           ├─ 校验 offset / len
           ├─ tmos_memcpy(pAttr->pValue, pValue, len)
           └─ bleUart_OnPhoneData(pValue, len)
                 ├─ 存到 CHAR2（便于手机回读校验）
                 ├─ BLE_UART_SendData()  ← 示例做了回环
                 └─ 回调应用层（可在此写串口）

上行：CH572 → 手机（Notify 0xFFE4）

业务代码
  │  BLE_UART_SendData(data, len)
  ▼
GATT_bm_alloc()   ← ★ 必须从协议栈内存池申请缓冲
  │                  （不能用自己的数组）
  ▼
tmos_memcpy(noti.pValue, data, len)
  │
  ▼
BLE_UART_Notify(connHandle, &noti)
  ├─ GATTServApp_ReadCharCfg() 检查手机是否已使能 Notify
  │     └─ 没使能 → 返回 bleIncorrectMode，并 GATT_bm_free() 释放
  ├─ pNoti->handle = attrTbl[CHAR4_VALUE_IDX].handle   ← 下标必须对
  └─ GATT_Notification()
        │
        ▼
   [ ATT Server ] ─► [ L2CAP ] ─► [ LL ] ─► [ 射频 ] ─► 手机
两个必须记住的内存管理规则
1. 发送缓冲必须从 GATT_bm_alloc() 申请，不能用局部数组或全局数组， 否则协议栈不知道这块内存归它管，异步发送时会读到已被覆盖的数据。
2. 发送失败必须 GATT_bm_free() 释放， 否则内存池会慢慢漏光，最终所有 BLE 操作都返回 bleMemAllocError。

6. 构建流程：从源码到 hex

方式 A 静态库构建

hal/HAL.c、RTC.c、SLEEP.c → .o

3
重新打包成完整静态库
ar rcs lib/libCH572BLE.a <HAL 的 3 个 .o> <协议栈 54 个 .o> → 679,924 字节，上层只需 -lCH572BLE
4
编译示例 + 链接
-lCH572BLE -lISP572，用 src/Ld/Link.ld
5
生成 hex + 四项自检
体积统计 · 指令集兼容性 · 能力拦截 · RAM 余量

方式 B ROM 镜像构建（三趟链接）

powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Target rom
为什么要三趟链接
跳转表的内容（每个 API 的绝对地址）依赖链接结果，而链接又需要跳转表存在 —— 循环依赖。解决办法是先占位、再收敛。
0
准备对象
解包协议栈 54 个 .o；编译 ROM 头部 / 中断转接 / 自动生成的兼容桩； 编译 ROM 自包含所需的 6 个外设驱动
1
趟 1：占位链接　不开 --gc-sections
跳转表先放 156 个 0 占位。目的：让每一个协议栈函数都被保留， 从 .map 里取到全部符号的地址。
这里开 gc-sections 会前功尽弃
--gc-sections 从"根"出发做可达性分析。占位跳转表不引用任何符号， 整个协议栈都会被判定为不可达而裁掉，map 里只剩头部几个符号。 若开启，可用 API 会从 94 个降到 14 个。
2
趟 2：生成跳转表 + 应用侧头文件
tools/rom_gen.py 用 map 里的符号地址填跳转表（汇编形式， 地址由链接器最终确定），同时生成 CH572BLE_ROM.h。
跳转表 ABI 沿用官方 CH59xBLE_ROM.h 的下标编号， 由 tools/rom_jt_extract.py 抽取（137 个函数 + 22 个 UUID）。
3
趟 3 / 4：迭代链接　开 --gc-sections
跳转表现在真实引用了所有要暴露的 API，它们成了 GC 根； 那些"只有主机角色才会走到"的死代码被裁掉 （连带解决它们引用的、PERI 库根本不存在的符号）。
然后用新的 map 重新生成跳转表，消除表自身占位带来的地址偏移，迭代两次收敛。
实测效果
趟 1（无 gc）全量链接 text 约 103 KB； 趟 5（有 gc）最终镜像 text 约 88 KB，裁掉约 15 KB 死代码。
5
最终链接 + 生成 hex/bin
不再重算跳转表，保证"表内容"与"镜像布局"严格一致。
产出 CH572BLE_ROM.hex（252,924 字节文本）与 .bin（89,900 字节纯二进制）。
6
ROM 方式应用构建
加 -DCH572BLE_ROM=1，编译 main_rom.c + 服务层 + HAL + 驱动， 用 src/Ld/Link_rom.ld 链接，不加 -lCH572BLE。

★ hex 是怎么生成的（重点）

一句话
把 WCH 给 CH572 的 BLE 协议栈（一个 .a 库文件） 重定位到固定地址，再在它开头放一张「函数跳转表」当目录， 最后用 objcopy 转成 .hex。

1. 五趟链接：为什么不能一次搞定

核心矛盾：跳转表的内容（每个 API 的绝对地址）依赖链接结果， 而链接又需要跳转表存在 —— 循环依赖。所以要「先占位、再收敛」。

输入材料

  • libCH572BLE_PERI.a
    WCH 官方协议栈，54 个 .o
  • rom/rom_entry.c
    镜像头部（魔数 + UUID 表）
  • rom/rom_support.c
    中断转接 + 应用钩子表
  • rom/rom_stub.c
    自动生成的兼容桩
  • src/StdPeriphDriver/*.c
    6 个外设驱动

链接过程

趟 1  占位链接（跳转表先放 156 个 0）
      ├ 目的：让每个函数都被保留，从 .map 拿到全部符号地址
      ├ 不开 --gc-sections（开了会把整个协议栈裁光）
      └ 产出：rom_pass1.map

趟 2  生成跳转表 + 应用头文件
      ├ tools/rom_gen.py 读 rom_pass1.map
      ├ 产出 build/rom/rom_jt.S        （跳转表汇编）
      └ 产出 include/CH572BLE_ROM.h    （应用侧头文件）

趟 3  迭代链接 #1（开 --gc-sections）
      ├ 跳转表现在真实引用所有 API → 它们成为 GC 根
      ├ 主机角色死代码被裁掉（连带解决它引用的缺失符号）
      └ 用新 map 重新生成跳转表，消除表自身占位带来的偏移

趟 4  迭代链接 #2 —— 再收敛一次

趟 5  最终链接
      └ 不再重算跳转表，保证「表内容」与「镜像布局」严格一致
         → CH572BLE_ROM.elf
趟 1 必须关掉 --gc-sections（实测踩过）
--gc-sections 从"根"出发做可达性分析。占位跳转表不引用任何符号， 于是整个协议栈被判为不可达而全裁掉 —— .map 里只剩头部几个符号。
实测：开 gc 时可用 API 只剩 14 个（正确应为 94 个）。
开 gc 的收益（实测）
趟 1（无 gc）全量链接 text 约 103 KB； 最终镜像约 89 KB —— 裁掉约 14 KB 只服务主机角色的死代码。

2. 镜像内部布局

ROM_BASE = 0x00020000

+0x00    8 字节    镜像标识：37 35 48 43 00 00 00 00
                             ↑ 小端读作 0x43483537 = "CH57"
+0x08   44 字节    UUID 表（22 项 × 2 字节）
                     00 18 = 0x1800 Generic Access
                     01 18 = 0x1801 Generic Attribute
                     00 28 = 0x2800 Primary Service
                     ...
+0x34  624 字节    函数跳转表（156 项 × 4 字节）
                     第  0 项 → 版本字符串地址
                     第  1 项 → tmos_rand
                     第  9 项 → tmos_start_task
                     第 46 项 → GAPRole_PeripheralInit
                     ...
之后              版本字符串 + 代码 + 只读数据

总计：89,316 字节（87.2 KB），地址范围 0x00020000 - 0x00035CE3
头部布局为什么能用 ASSERT 保证不出错
GNU ld 在拼接同一个输出段时按输入段名的字母序排列。 如果把魔数和 UUID 表都放进 .rom_header，字母序会让 UUID 排在魔数前面。
所以拆成 .rom_magic 与 .rom_uuid 两个独立段， 在链接脚本里按指定顺序拼，并用 ASSERT 强制校验总长必须 0x34 字节 —— 写错直接链接失败，不会等烧进芯片才发现。

3. 应用怎么调用 ROM（跳转表的作用）

应用侧头文件里的定义

#define FUNCITON_BASE_ADDRESSS \
        (LIB_FLASH_BASE_ADDRESSS + 0x34)

/* 读 (基址 + n*4) 处的 32 位值 = 第 n 个函数的地址 */
#define BLE_LIB_JT(n) \
        (*(uint32_t*)( FUNCITON_BASE_ADDRESSS + (n) * 4 ))

/* tmos_start_task = 把第 9 项当地址，转函数指针，调用 */
#define tmos_start_task \
  (( BOOL (*)(tmosTaskID, tmosEvents, tmosTimer) ) BLE_LIB_JT(9))

#define GAPRole_PeripheralInit \
  (( bStatus_t (*)(void) ) BLE_LIB_JT(46))

效果

应用编译时完全不需要协议栈代码， 只要知道「第 9 项是 tmos_start_task」就够了。

所以应用固件里没有那 74 KB 协议栈 —— text 从 80,276 字节降到 6,140 字节。

CH572 没有的 43 个 API（主机角色等）在表里填 0， 并且头文件里根本不定义这些宏 —— 误用会在编译期报错，而不是运行时跳到地址 0。

4. objcopy：从 elf 到 hex

命令

riscv-wch-elf-objcopy -O ihex   \
    build/rom/CH572BLE_ROM.elf  \
    lib/CH572BLE_ROM.hex

riscv-wch-elf-objcopy -O binary \
    build/rom/CH572BLE_ROM.elf  \
    lib/CH572BLE_ROM.bin

hex 文件长什么样

:020000040000FA        ← 基地址 = 0x0000
:100000003735484300000000...  ← +0x00 魔数 "CH57"
:100010000018011800280128...  ← +0x08 UUID 表
...
:00000001FF            ← 文件结束

每行格式：: + 字节数 + 地址 + 记录类型 + 数据 + 校验和。 HEX 是文本格式，每 16 字节数据要配 11 字符行头 + 校验和， 所以文件大小 ≈ 数据的 2.8 倍（251 KB 文本 ↔ 89 KB 实际数据）。

RAM 调优的实测教训

② 指令集兼容性

CH572 内核是 RV32IMBC：没有 A 扩展（原子指令）、 没有浮点单元。用 rv32imac 编译理论上可能生成 amo* / lr.w / sc.w，这些指令在 CH572 上会触发非法指令异常直接跑飞。 

python tools\isa_check.py build\out\ble_uart.elf

  函数符号: 676 个（只扫描这些真实代码区间）
  解码指令数: 28998
  [通过] 无 A 扩展原子指令、无浮点指令。
  [通过] 无标准 RISC-V 之外的 opcode。

实现要点：脚本先从 ELF 符号表取出全部 STT_FUNC 符号， 只对真实函数区间解码 —— 直接线性扫描整个 .text 会把里面的 字符串和跳转表当成指令，产生大量假阳性（会误报出十几条"浮点指令"和上百条"未知 opcode"，实际全是数据）。

一句话决策规则
你的设备是"被别人连"还是"主动去连别人"？
「被别人连」→ CH572 完全够用（成本低、引脚少）
「主动去连别人」→ 必须换 CH592（26 KB RAM / 448 KB Flash / 有 BLE ROM）

两种方式都用同一套能力宏把这条边界固化了：误调 CH572 没有的 API 会在编译期报错并打印中文提示，而不是等到链接期看一堆 undefined reference：

    GAPRole_CentralInit();          // CH592 走这里
#else

#endif
