# 最终结论：CH572 上 ROM 方式不可用（附完整实测证据）

> 本文基于**实机日志 + 静态分析**，不是推测。
> 相关：[`../MEMORY.md`](../MEMORY.md)、[`交接文档.md`](交接文档.md)

## 一、决定性对照实验

同一块 **CH572D-R0-1V1**、同一份应用代码，只换固件：

| 固件 | 结果 |
|---|---|
| **静态库方式** | ✅ 协议栈初始化正常，**手机能搜到设备、可正常广播** |
| ROM 方式 | ❌ 初始化全过、日志显示"正在广播"，但**射频中断从未进入 → 搜不到** |

## 二、ROM 方式的实测故障链

按时间顺序，实机日志逐层暴露的问题（**均已修复，但问题继续向下暴露**）：

| # | 现象 | 根因 | 状态 |
|---|---|---|---|
| 1 | 串口无输出 | `PRINT`/`_write` 靠 `#ifdef DEBUG` 启用 | ✅ 已修 |
| 2 | `head file error` | ROM 版本串与 `VER_FILE` 不一致 | ✅ 已修 |
| 3 | 卡在 `BLEInit 6/9` | 链接脚本 `FLASH_ROM_END` 撞 ISP 库函数名 | ✅ 已修 |
| 4 | MAC 读到全 0 | 出厂 MAC 未烧录 | ✅ 改用静态地址 |
| 5 | 卡在 `BLEInit 8/9` | ROM 的 `.data/.bss` 无人初始化 + 应用 RAM 覆盖 | ✅ 已修 |
| 6 | `mcause=2` 非法指令 | **向量表与 `.highcode` 同一输出段被重排覆盖** | ✅ 已修 |
| 7 | 向量表写入值错误 | `RomRam_Init()` 调用晚于 `InstallRomIrqHandlers()` | ✅ 已修 |
| 8 | **`mcause=4` Load access fault** | **见下节 —— 架构性缺陷** | ❌ **无法修复** |

修复 #7 后，关键指标**全部正确**：

```
向量表装配: 基址=0x20000800
  写入 [20]=0x000202DC  回读=0x000202DC  OK
  写入 [21]=0x000202FA  回读=0x000202FA  OK
Flash 读探测: ... 读到: 63 73 B6 00        <- 真实 MAC 数据
```

但随即出现**第 8 个问题**。

## 三、第 8 个问题：架构性缺陷（无法修复）

### 实机 HardFault 现场

```
mcause = 0x00000004   Load access fault
mepc   = 0x000024F4   <- 落在 HardFault_Handler 内部（0x23C2 + 0x132）
mtval  = 0x000202FA   <- ROM 的 LLE_IRQHandler 地址
RA     = 0x000025A6
```

两个关键点：

**① `mepc` 落在故障处理程序自己身上** → 典型的**二次异常**：
中断进 ROM 的 ISR 后，坏事发生；等 HardFault 处理程序去报告时，同样的坏事又发生了。

**② `mepc = 0x24F4` 落在一条指令的中间**：

```asm
24f2:  auipc a0,0x2       <- 32 位指令，占据 0x24F2-0x24F5
       └─ 0x24F4 是它的第 3 个字节
```

### 根因：协议栈的 `.highcode` 必须驻留 RAM，但 RAM 装不下

预编译的协议栈库（`libCH572BLE_PERI.a`）里，一批函数标了 `.highcode` 段，
**运行期地址写死在 RAM**（实测 `0x20000600 - 0x200012FE`）。原因：**擦写 Flash 时
CPU 不能从 Flash 取指**，这些函数必须在 RAM 里执行。

- **静态库方式能工作**：应用的 startup 把这 4,044 字节从 Flash 搬进 RAM
- **ROM 方式失效**：这段代码留在 ROM 镜像的 Flash 里（`0x2Fxxx-0x33xxx`），
  RAM 里对应地址是**空的**。协议栈（尤其是中断处理程序）一跳过去就取到空指令，
  栈被破坏 → 二次异常 → `mcause=4`

#### 为什么不能把 ROM 的 `.highcode` 也搬进 RAM

```
【静态库方式】—— 实测可用 ✓
  .highcode（必须在 RAM 执行） :   4044
  .data / .bss                 :    596 / 6272
  ------------------------------------
  合计                         :  10912  (10.66 KB)
  剩余给栈                     :   1376       <- 刚好够

【ROM 方式】—— 实测不可行 ✗
  ROM 镜像 .highcode（必须在 RAM）:  10496
  ROM 镜像 .data / .bss           :     68 / 1136
  应用 .data / .bss               :    484 / 5276
  ------------------------------------
  合计                            :  17460  (17.05 KB)
  RAM 总量                        :  12288  (12.00 KB)
  缺口                            :   5172  (5.05 KB)  ★
```

**ROM 的 `.highcode` 为什么是静态库的两倍多**：ROM 链接为保证跳转表里**每个** API
都有确定地址，**必须关闭 `--gc-sections`**（开了会把"没人调用"的函数裁掉、
跳转表项指向空地址）。关掉之后 `.highcode` 保留了全部带该段属性的函数。

#### 已排除的其他可能

| 假设 | 验证方式 | 结论 |
|---|---|---|
| ROM 的 RAM 变量被应用覆盖 | 比对 155 个 RAM 符号 vs 预留区 | ❌ 0 个越界，不是原因 |
| 两侧结构体字段错位 | 逐字段对比 + 从镜像读初值 | ❌ 完全一致 |
| 中断向量装配失败 | 运行时回读验证 | ❌ 写入/回读均正确 |
| 版本/时钟/射频配置 | 日志逐项确认 | ❌ 全部正常 |

## 四、结论与建议

### ROM 方式在 CH572 上不可行

需要 17.05 KB RAM，芯片只有 12 KB，**缺口 5.05 KB**。
这是**硬件资源约束**，不是代码写法能绕开的。

> 对比：CH592 有 26 KB RAM、448 KB Flash。CH59x 能做 ROM 方式，
> 是因为它的 RAM 是 CH572 的两倍多。

### 请使用静态库方式（已验证可用）

| 项目 | 数值 |
|---|---|
| 固件 | `build/out/ble_uart.hex` |
| 烧录 | `0x00000000`，**只需一个文件** |
| RAM 占用 | 10,912 字节（剩 1,376 给栈） |
| Flash 占用 | ~87 KB（可用 240 KB） |
| 应用代码 | 与 ROM 方式**完全相同** |

### 如果一定要 ROM 方式

只有两条路，都超出本工程范围：

1. **向 WCH 索取 CH572 专用 ROM 库**（像 CH59x 那样）
2. **要一份重新编译的协议栈库**：用 `-ffunction-sections` 编译，
   `.highcode` 只放真正必须在 RAM 的函数。**粗估压到 2 KB 以内即可行**
   （ROM 变量 1.2 + highcode 2 + 应用 5.8 ≈ 9 KB < 12 KB）

## 五、排查过程中修复的真实缺陷

虽然 ROM 方式最终不可行，但这 8 项都是**真实缺陷**，
其中 **#1、#3(部分)、#4、#6、#7 对静态库方式同样关键**：

| 缺陷 | 影响范围 |
|---|---|
| `R32_MISC_CTRL` 射频位未配置 | **两种方式**（射频完全不工作）★ |
| `SysTick_Handler` 落到启动文件死循环 | **两种方式**（43 秒后卡死）★ |
| 启动文件误用 `EXAM\SRC` 变体（`mstatus=0x88`） | **两种方式**★ |
| 出厂 MAC 全 0 → 手机忽略无效地址 | **两种方式**★ |
| 版本串与 `VER_FILE` 不一致 | ROM |
| `FLASH_ROM_END` 撞库函数名 | ROM |
| 向量表与 `.highcode` 同段被重排 | ROM |
| ROM 的 `.data/.bss` 无人初始化 | ROM |

**静态库方式现在能正常工作，依赖的正是 ★ 这四项修复。**

### 最重要的经验

> **给嵌入式工程加"可观测性"要放第一位。**
>
> 本次排查中，用户要求加的 **HardFault 现场打印**和**心跳日志**
> 各自一次就定位到了我猜了四五轮都没找到的问题：
>   * `mepc = 0x2000080E` → 向量表被 `.highcode` 覆盖
>   * `向量表[20]=0x20000890` → 补丁未生效（顺序问题）
>   * `mcause=4 + mtval=0x202FA` → ROM 的 ISR 依赖 RAM 代码
>
> 在加这两个工具之前，所有诊断都靠"改一处、烧一次、看现象"，效率极低。
