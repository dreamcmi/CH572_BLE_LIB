## 零、先选方案：静态库 vs ROM 镜像

本工程提供两种使用方式，**应用源码几乎完全一样**，只差一个 `main` 文件与编译宏：

| | 静态库方式 | ROM 镜像方式 |
|---|---|---|
| 库形式 | `lib/libCH572BLE.a` | `lib/CH572BLE_ROM.hex` / `.bin` |
| 应用头文件 | `ch572_ble.h` | `CH572BLE_ROM.h` |
| 编译宏 | 无 | `CH572BLE_ROM=1` |
| 链接参数 | `-lCH572BLE -lISP572` | 只 `-lISP572` |
| 链接脚本 | `src/Ld/Link.ld` | `src/Ld/Link_rom.ld` |
| 应用代码体积 | 80,276 字节 | **6,140 字节** |
| 应用 hex 大小 | 约 225 KB | **约 19 KB** |
| 可用栈空间 | 1,384 字节 | **1,712 字节** |
| 烧录 | 一个 hex 搞定 | 先烧 ROM 镜像（88 KB），再烧应用 |
| 适合场景 | 开发调试、小批量、不做 OTA | **量产、需要 OTA**（升级只传 19 KB） |

**建议**：开发阶段用静态库方式（省事），量产切 ROM 方式（省 Flash、省 OTA 流量、
升级不动协议栈所以更安全）。

## 一、环境准备

### 1.1 硬件

- 一块 CH572 开发板（如 CH572D-R0 / CH572Q-DG-R0，见 `CH572EVT-1.4/EVT/PUB/`）
- WCH 的 WCH-Link / WCH-LinkE 调试下载器
- 可选：串口工具（用于看 `PRINT` 输出）

### 1.2 软件（二选一或都装）

**方案 1：MounRiver Studio（推荐用于实际开发与下载）**

从 WCH 官网下载安装 MounRiver Studio（MRS）。
本工程也能用 MounRiver Studio 2，但**建议用 MRS1**，因为 EVT 包里的 `.cproject`
是 MRS1 格式。

**方案 2：任意 RISC-V GCC 工具链（用于命令行构建 / CI 验证）**

本工程能自动探测几种工具链：

| 工具链 | 是否推荐 | 说明 |
|---|---|---|
| `riscv-wch-elf-gcc` | ★★ **首选** | **MounRiver Studio 2 自带**，WCH 定制版，认识 `mcpy` 指令与 `WCH-Interrupt-fast` 硬件压栈中断 |
| `riscv-none-embed-gcc` | ★★ 首选 | MounRiver Studio 1 自带，同样是 WCH 定制版 |
| `riscv-none-elf-gcc` | ★ 推荐 | 新版 MRS / xPack RISC-V GCC |
| `riscv32-esp-elf-gcc` | 可用于验证 | ESP-IDF 自带。脚本会自动加 `-DINT_SOFT -DUSE_STD_MCPY` 降级 |
| `riscv64-unknown-elf-gcc` | 可用于验证 | 通用工具链，同样需要上面两个降级宏 |

**MounRiver Studio 2 的工具链实际位置**（脚本会自动探测，不用手工填）：

```
D:\MounRiver\MounRiver_Studio2\resources\app\resources\win32\
    components\WCH\Toolchain\RISC-V Embedded GCC12\bin\riscv-wch-elf-gcc.exe
    →  xPack GNU RISC-V Embedded GCC 12.2.0
```

自动探测失败时手工指定：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Target all `
    -Toolchain "D:\MounRiver\MounRiver_Studio2\resources\app\resources\win32\components\WCH\Toolchain\RISC-V Embedded GCC12"
```

### 两个工具链的实测差异

| | 通用工具链（ESP-IDF GCC 14.2） | **WCH 工具链（GCC 12.2）** |
|---|---|---|
| `mcpy` 私有指令 | ✗ 需 `-DUSE_STD_MCPY` 退化成逐字节拷贝 | ✓ 实测生成 3 处 `mcpy` |
| 中断硬件压栈 | ✗ 需 `-DINT_SOFT` 降级 | ✓ `mret` 前无寄存器保存代码 |
| ROM 镜像 bin | 89,900 字节 | **89,316 字节** |
| 应用 text（ROM 方式） | 6,360 字节 | **6,140 字节** |
| 可用栈 | 1,232 字节 | **1,384 字节** |

> 详细原理（为什么通用工具链不认这两个扩展、降级后差在哪）
> 见 [`从零开始-ROM镜像制作教程.md` 第 1 章](从零开始-ROM镜像制作教程.md#第-1-章-工具链用的是哪一个)。

### 1.3 需要的 Python（可选，但强烈建议）

`tools/` 下的自检脚本需要 Python 3.8+。构建流程会自动调用
`tools/isa_check.py` 做指令集兼容性自检；没有 Python 时会跳过这一步（不影响编译）。

### 3.2 导入并编译

1. 打开 MounRiver Studio
2. `File` → `Import` → `General` → `Existing Projects into Workspace` → `Next`
3. `Select root directory` 选择：

   ```
   ...\CH572_BLE_LIB\examples\ble_uart
   ```

4. 勾选列表里出现的 `ble_uart` 工程 → `Finish`
5. 点工具栏的 **Build**（锤子图标）编译
6. 点 **Download** 烧录

### 3.3 工程结构说明（导入后你会看到）

```
ble_uart/                     ← 你的工程
├── src/                      ← 示例源码（main.c / ble_uart.c / ble_uart_service.c）
├── include/                  ← 示例自己的头文件
├── ble_include  ─┐
├── ble_hal       │ 链接资源（Linked Resources），实际指向 ..
├── ble_lib       │ 即 CH572_BLE_LIB 根目录下的同名文件夹
└── ble_src      ─┘
```

`ble_*` 这几个不是拷贝，是**链接**。好处是：改一次 `hal/HAL.c`，所有示例工程同步生效；
整个 `CH572_BLE_LIB` 目录可以随意搬到别的路径，工程依然有效
（用 `PARENT-2-PROJECT_LOC` 相对定位）。

### 3.4 想在 MRS 里新建自己的工程

最省事的做法：

1. 复制 `examples/ble_uart` 整个目录，改名成你的工程名；
2. 把 `.project` 里的 `<name>ble_uart</name>` 改成你的工程名；
3. 把 `src/` 下的示例代码换成你自己的；
4. 如果新工程不在 `examples/` 下，需要相应调整 `.project` 里的
   `PARENT-2-PROJECT_LOC`（每往上一级就加一）。

### 4.3 构建流程做了什么

```
┌─ 1. 探测工具链（MounRiver / ESP-IDF / PATH 三种途径）

│     -T src/Ld/Link.ld

├─ 8. 输出体积统计（size）+ 最大符号（nm）
```

> 方便对比体积。

### 5.2 烧录顺序

```
① lib\CH572BLE_ROM.hex          →  烧到 0x00020000 起
② build\out\ble_uart-rom.hex    →  烧到 0x00000000 起
                                   （app 主体在 0x00000 起的一整块连续空间里）
```

用 MounRiver Studio 的下载工具或 WCHISPTool 都行。
**ROM 镜像只需要烧一次**；以后升级只烧应用固件。

### 5.3 应用侧必须做的两件事

ROM 方式下有两件事和静态库方式不同，漏做会导致 BLE 完全不能工作：

#### ① 装 ROM 中断钩子

BLE 的基带中断（BB）与链路层中断（LLE）处理函数在 ROM 里。
应用的 `startup_CH572.S` 里这两个中断是"弱定义 + 死循环"，
不替换掉的话射频中断一触发就停在死循环。

```c
#include "CONFIG.h"     /* 定义 CH572BLE_ROM=1 时自动切到 CH572BLE_ROM.h */

static void InstallRomIrqHandlers(void)
{
    static rom_app_hooks_t hooks;

    tmos_memset(&hooks, 0, sizeof(hooks));
    hooks.magic = ROM_HOOK_MAGIC;

    const rom_handles_t *h = CH572BLE_ROM_GetHandles();  /* 取 ROM 中断入口 */
    if (h && h->magic == ROM_HANDLE_MAGIC)
    {
        hooks.ble_irq_handler = h->bb_irq;    /* 基带中断 → ROM 实现 */
        hooks.lle_irq_handler = h->lle_irq;   /* 链路层中断 → ROM 实现 */
    }
    hooks.rtc_irq_handler = RTC_IRQHandler;   /* RTC 中断由应用处理 */

    PRINT("ROM 版本: %s\n", CH572BLE_ROM_Init(&hooks));   /* 注册并取版本号 */
}
```

#### ② 链接时不要加 `-lCH572BLE`

加了的话等于把静态库版协议栈又链一份进来，体积白涨还可能符号冲突。

```make
# 正确
LIBS    = -Llib -lISP572 -lm
LDFLAGS = -nostartfiles -Tsrc/Ld/Link_rom.ld -Wl,--gc-sections \
          --specs=nano.specs --specs=nosys.specs
```

### 5.4 完整最小示例（ROM 方式）

见 `examples/ble_uart/src/main_rom.c`，核心骨架：

```c
#include "CONFIG.h"
#include "ble_uart_service.h"

/* 协议栈代码在 ROM，但它的数据（内存池、控制块）仍在 RAM，由应用提供 */
__attribute__((aligned(4))) uint32_t MEM_BUF[BLE_MEMHEAP_SIZE / 4];

int main(void)
{
    R16_PIN_ALTERNATE &= ~RB_PIN_DEBUG_EN;
    HSECFG_Capacitance(HSECap_18p);
    SetSysClock(CLK_SOURCE_HSE_PLL_100MHz);

    InstallRomIrqHandlers();     /* ★ 必须：装 ROM 中断钩子 */
    CH57x_BLEInit();             /* 启动协议栈 */
    HAL_Init();
    GAPRole_PeripheralInit();
    BLE_UART_Init();

    while (1)
    {
        TMOS_SystemProcess();    /* ROM 方式下这个宏指向 ROM 里的调度器 */
    }
}
```

### 5.7 哪些 API 可用，哪些不可用

完整对照表在 `lib/CH572BLE_ROM_JT.md`，逐项标了状态。

- **94 个可用**：TMOS 调度、GAP 从机、GATT Server、配对绑定、连接管理、内存管理、UUID 表
- **43 个不可用**：主机（Central）/ 观察者 / GATT 客户端 / BLE 5.x 高级特性

不可用的那些在 `CH572BLE_ROM.h` 里被**刻意省略** ——
误用会在**编译期**报错（`implicit declaration of function`），
而不是运行时跳到地址 0 跑飞。

## 五点五、换了协议栈库之后怎么重新生成

如果 WCH 发布了新的 CH572EVT，或者你自己替换了 `lib\libCH572BLE_PERI.a`，
需要**重新生成 hex 与头文件**（不能只换 hex，原因见下）。

### 一条命令

**`scripts\make_rom.ps1` 是本工程唯一的 ROM 产物生成入口**，
只做"库编译 + 头文件生成"两件事，不做其他任务。

```powershell
cd CH572_BLE_LIB

# 库已经放好了，重新生成
powershell -ExecutionPolicy Bypass -File scripts\make_rom.ps1

# 换一个新库（会先备份工程内原库，再替换）
powershell -ExecutionPolicy Bypass -File scripts\make_rom.ps1 `
    -Lib "D:\CH572EVT-1.5\EVT\EXAM\BLE\LIB\libCH572BLE_PERI.a"

# 换个 ROM 基址
powershell -ExecutionPolicy Bypass -File scripts\make_rom.ps1 -RomBase 0x00008000
```

脚本内部走五趟链接：解包 → 占位链接采地址 → 生成跳转表与头文件 →
迭代链接收敛 → 输出 hex / bin。

### 为什么不能只换 hex

| 新库带来的变化 | 后果 |
|---|---|
| 新增 API | 跳转表扩容，编号可能重排 → 头文件必须重建 |
| 删除 API | 原本可用的宏可能失效 → 头文件必须重建 |
| 代码实现改了 | 各 API 绝对地址全变 → hex 必须重建 |
| 库变大/变小 | 镜像结束地址变了 → `Link_rom.ld` 的 `FLASH_ROM_END` 可能要调 |

> ⚠️ **头文件变了必须重编应用**。否则应用会按旧的跳转表编号调用，
> 轻则功能异常，重则跳到无效地址跑飞。

### 换完头文件要重编应用

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Target example
```

完整说明（含四种情况、换库后要检查什么、常见问题）见
[`lib更新后如何重新生成.md`](lib更新后如何重新生成.md)。

```
├── lib/

│   └── libISP572.a            ← CH572 官方 ISP/Flash 库（必需）

│   ├── CH572BLEPeri_LIB.h     ← 官方协议栈头文件（必须，被 ch572_ble.h 引用）
│   ├── CH57x_*.h              ← 标准外设驱动头文件（必须）
│   ├── CH572SFR.h             ← 寄存器定义（必须）

    ├── Startup/startup_CH572.S
```

### 5.2 编译参数

```make
# 架构
ARCH    = -march=rv32imac_zicsr_zifencei -mabi=ilp32 -mcmodel=medany -msmall-data-limit=8

# 优化（-Os 体积最小；-O2 更快但更大）
OPT     = -Os

# 其它
CFLAGS  = $(ARCH) $(OPT) -ffunction-sections -fdata-sections -fno-common -g
CFLAGS += -Iinclude -Isrc/StdPeriphDriver -Isrc/RVMSIS

# 非 WCH 工具链追加（MRS 自带工具链不需要）
CFLAGS += -DINT_SOFT -DUSE_STD_MCPY

# 链接
LDFLAGS = $(ARCH) -nostartfiles -Tsrc/Ld/Link.ld \
          -Wl,--gc-sections --specs=nano.specs --specs=nosys.specs
LIBS    = -Llib -lCH572BLE -lISP572 -lm
```

> `-march` 里必须带 `_zicsr_zifencei`，否则启动文件里的 `csrw` 指令无法汇编。
> `-ffunction-sections -fdata-sections` 配合 `-Wl,--gc-sections` 能把没用到的
> 协议栈函数裁掉，对 240 KB Flash 的 CH572 很重要。

### 5.3 最小 main.c 骨架

```c
#include "CONFIG.h"          /* 这一个头文件就够了 */

/* 协议栈内存堆：必须由应用提供，必须 4 字节对齐 */
__attribute__((aligned(4))) uint32_t MEM_BUF[BLE_MEMHEAP_SIZE / 4];

int main(void)
{
    /* 1. 关调试口（可选，释放 PA7/PA8） */
    R16_PIN_ALTERNATE &= ~RB_PIN_DEBUG_EN;

    /* 2. 系统时钟：BLE 要求 HSE 32MHz + PLL 到 100MHz */
    HSECFG_Capacitance(HSECap_18p);
    SetSysClock(CLK_SOURCE_HSE_PLL_100MHz);

    /* 3. 初始化协议栈（填配置、注册回调、启动、建 RTC 时基） */
    CH57x_BLEInit();

    /* 4. 初始化 HAL 任务 */
    HAL_Init();

    /* 5. 初始化 GAP 从机角色 */
    GAPRole_PeripheralInit();

    /* 6. 初始化你自己的 GATT 服务与业务 */
    MyApp_Init();

    /* 7. 主循环：所有 BLE 事件都在 TMOS_SystemProcess() 里处理 */
    while(1)
    {
        TMOS_SystemProcess();
    }
}
```

**顺序不能乱**：时钟 → `CH57x_BLEInit()` → `HAL_Init()` → `GAPRole_PeripheralInit()` → 应用初始化 → 主循环。

**主循环里绝对不要写阻塞逻辑**（不要 `delay_ms(1000)`、不要死等串口），
否则会错过 BLE 的连接事件时序，表现为「连上就掉线」或者「根本连不上」。
需要延时请用 `tmos_start_task()` 注册 TMOS 定时事件。

## 七、示例代码导读：一个 BLE 从机是怎么写起来的

以 `examples/ble_uart/` 为例，三个文件分工明确：

| 文件 | 职责 | 对应 BLE 协议层 |
|---|---|---|
| `main.c` | 时钟、`MEM_BUF`、启动顺序、主循环 | 系统层 |
| `ble_uart.c` | 广播数据、连接参数、配对绑定、连接状态处理 | GAP 层 |
| `ble_uart_service.c` | 属性表、读回调、写回调、Notify | GATT 层 |

### 6.1 GAP 层：怎么把设备"广播"出去

```c
/* 广播数据：Flags + 服务 UUID。格式是 [长度][类型][数据...] */
static uint8_t bleUartAdvData[] = {
    0x02, GAP_ADTYPE_FLAGS,
    GAP_ADTYPE_FLAGS_GENERAL | GAP_ADTYPE_FLAGS_BREDR_NOT_SUPPORTED,
    0x03, GAP_ADTYPE_16BIT_MORE,
    LO_UINT16(BLE_UART_SERV_UUID), HI_UINT16(BLE_UART_SERV_UUID),
};

/* 在初始化里配置进去 */
GAPRole_SetParameter(GAPROLE_ADVERT_DATA, sizeof(bleUartAdvData), bleUartAdvData);
GAPRole_SetParameter(GAPROLE_SCAN_RSP_DATA, sizeof(bleUartScanRspData), bleUartScanRspData);
GAPRole_SetParameter(GAPROLE_ADVERT_ENABLED, sizeof(uint8_t), &advEnable);

/* 最后启动设备（延迟一个 TMOS 事件，确保初始化都完成了） */
tmos_set_event(bleUartTaskID, BLE_UART_START_DEVICE_EVT);
/* → 在事件处理里：GAPRole_PeripheralStartDevice(taskID, &bondCBs, &roleCBs); */
```

> 注意：广播数据和扫描响应加起来不能超过 31 字节（BLE 4.x 限制）。
> 完整设备名放扫描响应里，广播数据里只放 Flags + UUID，这样最省。

### 6.2 GATT 层：属性表怎么写

属性表是 GATT 服务的骨架，**顺序固定**：

```c
static gattAttribute_t attrTbl[] = {
    /* [0] 服务声明 */
    { {ATT_BT_UUID_SIZE, primaryServiceUUID}, GATT_PERMIT_READ, 0, (uint8_t *)&myService },

    /* [1] 特征值1 声明 */
    { {ATT_BT_UUID_SIZE, characterUUID}, GATT_PERMIT_READ, 0, &char1Props },
    /* [2] 特征值1 的值 */
    { {ATT_BT_UUID_SIZE, char1UUID}, GATT_PERMIT_READ | GATT_PERMIT_WRITE, 0, char1Value },
    /* [3] 特征值1 的用户描述（可选但建议加，手机 App 上能看到） */
    { {ATT_BT_UUID_SIZE, charUserDescUUID}, GATT_PERMIT_READ, 0, char1UserDesp },

    /* [4] 特征值2 声明 … 依此类推 */

    /* 带 Notify 的特征值，多一个 CCC 描述符 */
    { {ATT_BT_UUID_SIZE, characterUUID}, GATT_PERMIT_READ, 0, &char4Props },
    { {ATT_BT_UUID_SIZE, char4UUID}, 0, 0, char4Value },          /* ← 记住这一项的下标！ */
    { {ATT_BT_UUID_SIZE, clientCharCfgUUID},
      GATT_PERMIT_READ | GATT_PERMIT_WRITE, 0, (uint8_t *)char4Config },
    { {ATT_BT_UUID_SIZE, charUserDescUUID}, GATT_PERMIT_READ, 0, char4UserDesp },
};
```

**两个最容易踩的坑**：

1. **Notify 特征值的属性表下标**（示例里是 `11`）必须和代码里的宏
   `BLE_UART_CHAR4_VALUE_IDX` 一致。发通知时要靠这个下标拿 handle：
   ```c
   pNoti->handle = attrTbl[BLE_UART_CHAR4_VALUE_IDX].handle;
   ```
   下标写错 → 通知发到错误的属性上，手机收不到。

2. **断连时要复位 CCC**，否则下次连接会残留上次的 Notify 使能状态：
   ```c
   static void HandleConnStatusCB(uint16_t connHandle, uint8_t changeType)
   {
       if ((changeType == LINKDB_STATUS_UPDATE_REMOVED) ||
           ((changeType == LINKDB_STATUS_UPDATE_STATEFLAGS) && !linkDB_Up(connHandle)))
       {
           GATTServApp_InitCharCfg(connHandle, char4Config);
       }
   }
   ```

### 6.3 发通知（设备 → 手机）

```c
bStatus_t BLE_UART_SendData(uint8_t *data, uint16_t len)
{
    attHandleValueNoti_t noti;
    uint16_t allocLen;

    if (connHandle == GAP_CONNHANDLE_INIT) return bleNotConnected;

    /* 关键：发送缓冲必须从 GATT 内存池申请，不能用自己的数组 */
    noti.pValue = (uint8_t *)GATT_bm_alloc(connHandle, ATT_HANDLE_VALUE_NOTI,
                                           len, &allocLen, 0);
    if (noti.pValue == NULL) return bleMemAllocError;   /* 内存池满了 */

    noti.len = len;
    tmos_memcpy(noti.pValue, data, len);

    if (BLE_UART_Notify(connHandle, &noti) != SUCCESS)
    {
        /* 关键：发送失败必须释放，否则会漏内存直到协议栈卡死 */
        GATT_bm_free((gattMsg_t *)&noti, ATT_HANDLE_VALUE_NOTI);
    }
    return SUCCESS;
}
```

### 6.4 收数据（手机 → 设备）

手机写特征值会走到写回调里：

```c
static bStatus_t WriteAttrCB(uint16_t connHandle, gattAttribute_t *pAttr,
                             uint8_t *pValue, uint16_t len, uint16_t offset, uint8_t method)
{
    uint16_t uuid = BUILD_UINT16(pAttr->type.uuid[0], pAttr->type.uuid[1]);

    switch (uuid)
    {
        case BLE_UART_CHAR3_UUID:                  /* 透传下行通道 */
            if (offset != 0) return ATT_ERR_ATTR_NOT_LONG;
            if (len > sizeof(char3Value)) return ATT_ERR_INVALID_VALUE_SIZE;

            /* 1. 存下来 */
            tmos_memcpy(pAttr->pValue, pValue, len);
            /* 2. 交给业务处理 —— 真实产品在这里把数据写到串口 */
            OnPhoneData(pValue, len);
            break;

        case GATT_CLIENT_CHAR_CFG_UUID:            /* 手机开/关 Notify */
            status = GATTServApp_ProcessCCCWriteReq(connHandle, pAttr, pValue,
                                                    len, offset, GATT_CLIENT_CFG_NOTIFY);
            break;
    }
    return status;
}
```

### 6.5 用手机验证示例

1. 编译烧录 `ble_uart.hex`
2. 手机装任意 BLE 调试 App（nRF Connect / 沁恒的 BLE 调试助手 / LightBlue）
3. 扫描，找到名为 **`CH572-BLE-UART`** 的设备，连接
4. 展开服务 `0xFFE0`：
   - 读 `0xFFE1` → 应该返回 `0x11`
   - 写 `0xFFE3` → 设备会把数据原样通过 `0xFFE4` 回传（示例做了回环）
   - 点 `0xFFE4` 旁边的三个箭头（启用 Notify）→ 然后再写 `0xFFE3`，
     就能看到 `0xFFE4` 收到通知
   - 读 `0xFFE5` → 未配对时会返回「权限不足」（演示认证读）

## 八、配置项详解

全部在 `include/ch572_ble.h` 里，可以直接改，也可以在工程预定义宏里覆盖。

### 7.1 内存与缓冲区

| 宏 | 默认 | 说明与调优建议 |
|---|---|---|
| `BLE_MEMHEAP_SIZE` | `512*10`（5120） | 协议栈 RAM 堆。**这是 RAM 消耗最大的一项**。<br>5 KB 实测够跑从机全功能；<br>调到 6 KB → 应用栈只剩 ~224 字节（太紧）；<br>要开大 MTU（`BLE_BUFF_MAX_LEN` > 27）时按每档 +512 递增 |
| `BLE_BUFF_MAX_LEN` | `27` | 单包最大长度。`27` → `ATT_MTU = 23`（BLE 4.0 默认）<br>要跑大数据吞吐可设 `251`（→ MTU 247），但显著吃 RAM |
| `BLE_BUFF_NUM` | `3` | 控制器缓存的收发包数量。必须 ≥ 连接数 |
| `BLE_TX_NUM_EVENT` | `1` | 每个连接事件最多发几个包。调到 `4~6` 可提高吞吐，但更耗电、吃更多缓存 |

### 7.2 射频

| 宏 | 默认 | 说明 |
|---|---|---|
| `BLE_TX_POWER` | `LL_TX_PWR_0_DBM` | 发射功率，可选 `LL_TX_PWR_MINUS_25_DBM` ~ `LL_TX_PWR_7_DBM` |
| `BLE_CALIBRATION_ENABLE` | `TRUE` | 是否开启定时频偏校准（建议开着） |
| `BLE_CALIBRATION_PERIOD` | `120000` | 校准周期，单位 ms |
| `TEM_SAMPLE` | `TRUE` | 是否用温度采样辅助校准 |

### 7.3 地址与存储

| 宏 | 默认 | 说明 |
|---|---|---|
| `BLE_MAC` | `FALSE` | `FALSE` 用芯片出厂 MAC；`TRUE` 用 `main.c` 里的 `MacAddr[6]`（**小端序**） |
| `BLE_SNV` | `TRUE` | 是否保存配对绑定信息（关掉就每次都要重新配对） |
| `BLE_SNV_ADDR` | `0x1F000` | SNV 存放起始地址。必须落在用户 Flash 区内、256 字节对齐，且**不能落进 ROM 镜像区间** |
| `BLE_SNV_BLOCK` | `256` | SNV 块大小，必须是 Flash 擦除粒度 |
| `BLE_SNV_NUM` | `1` | SNV 块数量 |

> ⚠️ `BLE_SNV_ADDR` 必须避开你的程序代码区，**也不能落进 ROM 镜像区间**。默认 `0x1F000` 紧邻 ROM 之前，是 240 KB 用户区
> 最末尾附近（`0x3C000` 是理论上限）。如果你的固件编出来接近满，记得把地址往前挪，
> 或者关掉 SNV。

### 7.4 时钟与低功耗

| 宏 | 默认 | 说明 |
|---|---|---|
| `CLK_OSC32K` | `1` | RTC 时钟源：`0`=外部 32768Hz，`1`=内部 32000Hz，`2`=内部 32768Hz |
| `HAL_SLEEP` | `FALSE` | 是否开启低功耗睡眠。开启后 `HAL_IdleCB` 会调 `CH57x_LowPower()` |

> 需要 RTC 走时准确（比如要做精确的连接间隔管理）建议用外部 32.768 kHz 晶振（`CLK_OSC32K=0`）。

### 7.5 调试

| 宏 | 说明 |
|---|---|
| `DEBUG` | 定义后 `PRINT(...)` 才有输出（走 UART）。`build.ps1 -Defines DEBUG=1` 或在 MRS 里加宏 |
| `INT_SOFT` | 非 WCH 工具链必须（构建脚本自动加） |
| `USE_STD_MCPY` | 非 WCH 工具链必须（构建脚本自动加） |

## 九、从 CH592 移植代码到 CH572

### 8.1 移植检查清单

| 检查项 | 处理方式 |
|---|---|
| 头文件 `CH59xBLE_LIB.h` | 改成 `ch572_ble.h`（或直接 `CONFIG.h`） |
| 初始化函数 `CH59x_BLEInit()` | 改成 `CH57x_BLEInit()` |
| 宏 `CH59xBLE_ROM=1` | **删掉**。CH572 没有 ROM 模式 |
| 链接库 `-lCH59xBLE` | 改成 `-lCH572BLE -lISP572` |
| 启动文件 `startup_CH592.S` | 换成 `startup_CH572.S` |
| 链接脚本 `Link.ld` | 换成 CH572 的（FLASH 240 K，RAM 12 K） |
| 标准外设 API | CH59x 的 `CH59x_gpio.c` → CH572 的 `CH57x_gpio.c`，函数名基本一致，个别 GPIO 端口/引脚定义不同 |
| 用了 Central / Observer / GATT Client API | **必须改方案或换芯片**（用 `#if CH572_BLE_HAS_CENTRAL` 判断） |
| 用了 BLE 5.x 扩展广播 / 周期同步 | **必须改方案或换芯片** |
| 用了 `RF_FrequencyHopping*` | **必须改方案或换芯片** |
| 多从机并发（`PERIPHERAL_MAX_CONNECTION > 1`） | 改成 `1` |
| ROM 版本工程（`OnlyUpdateApp_*`） | 不适用，CH572 没有这套 |

### 8.2 用能力宏做条件编译

把两种芯片的代码放在同一个工程里：

```c
#include "ch572_ble.h"

void BLE_App_Init(void)
{
#if CH572_BLE_HAS_CENTRAL
    /* ===== CH592：主从一体方案 ===== */
    GAPRole_CentralInit();
    GAPRole_PeripheralInit();
    /* … */
#else
    /* ===== CH572：纯从机方案 ===== */
    GAPRole_PeripheralInit();
    /* … */
#endif
}
```

编译 CH572 版本时，`#if` 分支不会参与编译，
所以即使分支里写了 CH572 没有的 API 也不会报错（宏展开被预处理跳过了）。

**但如果是无条件调用**，就会在编译期被抓出来：

```c
GAPRole_CentralInit();   /* 未包在 #if 里 */
```

```
error: call to '_ch572_ble_missing_api' declared with attribute error:
       CH572 BLE 固件库不提供该 API，请检查平台能力宏 CH572_BLE_HAS_xxx
```

## 十、资源占用与调优

### 9.1 实测基线（`ble_uart` 示例，`-Os`）

```
Flash:  text = 80,276 字节  (78.4 KB)   占 240 KB 的 33%
        data =    588 字节
        hex 文件实际数据 81,504 字节 (79.6 KB)

RAM:    bss  =  6,272 字节
        ├─ MEM_BUF（协议栈堆）5,120 字节
        └─ 其它静态变量        1,152 字节
        栈空间 ≈ 1,232 字节（_ebss 0x20002B30 → 栈顶 0x20003000）
```

### 9.2 Flash 不够怎么办

CH572 的应用 Flash 是 240 KB，从机方案只用了 79 KB，一般不会不够。如果确实紧张：

1. **确认 `-ffunction-sections -fdata-sections -Wl,--gc-sections` 都开了**
   （本工程默认开启。不开的话整个协议栈会被链进去，体积会大很多）
2. **改用 `-Os`**（本工程默认）
3. **关掉不用的功能**：
   - `BLE_SNV = FALSE` → 省掉 `tmos_snv_*` 和 Flash 读写回调
   - `TEM_SAMPLE = FALSE`、`BLE_CALIBRATION_ENABLE = FALSE` → 省掉校准相关代码
4. **关掉调试打印**：不定义 `DEBUG`（`printf` 系列会带进不少代码）

### 9.3 RAM 不够怎么办（更常见）

按"省 RAM 效果从大到小"排序：

1. **调小 `BLE_MEMHEAP_SIZE`**
   每减 512 字节就多 512 字节给应用。但不要低于 `512*8 = 4096`，
   否则连接建立后协议栈会分配失败。
   调完**一定要实测**：能广播 → 能连接 → 能收发数据 → 能配对。

2. **调小 `BLE_BUFF_MAX_LEN`**
   默认 `27`（MTU 23）。如果只需要发几个字节的控制指令，可以调到 `27` 已经是最小可用值了。
   反过来，**如果你不需要大 MTU，就不要调大它**。

3. **减少 `BLE_BUFF_NUM`**（默认 3，最低建议 2）

4. **`BLE_TX_NUM_EVENT = 1`**（默认已是 1）

5. **关掉 SNV**（`BLE_SNV = FALSE`）—— 省下 SNV 缓存和 Flash 相关逻辑

6. **检查你自己的全局变量**：大数组改成动态分配或者用联合体复用；
   字符串常量加 `const` 放进 Flash 而不是 RAM。

7. **减小栈需求**：避免深层递归、避免在栈上开大数组
   （`uint8_t buf[256]` 在 12 KB RAM 的芯片上是很奢侈的）。

### 9.4 吞吐调优

要跑高速率（比如串口透传跑满）：

```c
#define BLE_BUFF_MAX_LEN     251    /* ATT_MTU = 247 */
#define BLE_BUFF_NUM         5      /* 多缓存几包 */
#define BLE_TX_NUM_EVENT     6      /* 每个连接事件多发几包 */
```

同时把连接间隔调小（在 `ble_uart.c` 里）：

```c
#define BLE_UART_CONN_INTERVAL_MIN      8    /* 10 ms */
#define BLE_UART_CONN_INTERVAL_MAX      8
```

以及让手机端也请求 `MTU = 247`。注意这样 RAM 会更紧张，`BLE_MEMHEAP_SIZE` 要同步加大。

## 十一、FAQ 与排错

### Q1: 编译报 `undefined reference to 'CH57x_BLEInit'`

说明没用 `hal/HAL.c`，或者 `libCH572BLE.a` 不是本工程构建出来的那个。
确认链接了 `-lCH572BLE`（**不是** `-lCH572BLE_PERI`），
并且 `lib/libCH572BLE.a` 是本工程构建生成的（应该 ≈ 680 KB）。

### Q2: 编译报 `undefined reference to 'FLASH_EEPROM_CMD'`

缺少 ISP/Flash 库。链接参数加上 `-lISP572`。

### Q3: 编译报 `unrecognized opcode 'mcpy'`

你用的是非 WCH 工具链，但没加 `-DUSE_STD_MCPY`。
用 `scripts/build.ps1` 会自动加；手工构建请自己加。

### Q4: 编译报 `BOM` 或脚本语法错误（PowerShell 脚本）

`build.ps1` 里有中文，Windows PowerShell 5.1 需要文件带 UTF-8 BOM 才能正确解析。
如果被编辑器去掉了 BOM，跑一下：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\fix-ps1-bom.ps1
```

### Q5: 烧录后串口没输出（`PRINT` 不打印）

1. 没有定义 `DEBUG` 宏（默认不定义）→ 用 `-Defines DEBUG=1` 重新编译
2. 串口引脚不对 → 默认是 `UART_TX_REMAP_PA3` / `UART_RX_REMAP_PA2`，
   按你的板子改 `main.c` 里的 `UART_Remap()`
3. 波特率 → `UART_DefInit()` 默认 115200

### Q6: 手机搜不到设备

1. 确认板子在跑（`PRINT` 能打印出 `CH572_BLE_PERI_LIB_V1.3`）
2. **32 MHz 晶振没起振** —— 这是最常见的原因。
   检查 `HSECFG_Capacitance(HSECap_18p)` 的负载电容是否匹配你的晶振；
   量一下晶振是否起振
3. 确认调用了 `GAPRole_PeripheralStartDevice()`
4. 确认天线匹配网络正常
5. 广播数据格式错误（长度字节和实际数据不匹配）会导致广播包非法

### Q7: 能连上但很快掉线

1. **主循环里有阻塞代码** —— 检查 `while(1)` 里是不是只有 `TMOS_SystemProcess()`
2. **RAM 不够**，协议栈分配失败。看 `.map` 里 `_ebss` 到栈顶的余量，
   试着调大 `BLE_MEMHEAP_SIZE`
3. 连接参数不合理（比如 `connTimeout` 太小）
4. 电源不稳（射频发射瞬间电流冲高）—— 检查 LDO 和去耦电容

### Q8: 发送 Notify 失败 / 手机收不到

1. **手机没使能 Notify**（没写 CCC 描述符）→ 代码里会返回 `bleIncorrectMode`
2. **Notify 特征值在属性表里的下标写错了** → 检查 `pNoti->handle` 取的是不是
   正确那一条属性的 handle
3. **`GATT_bm_alloc()` 返回 NULL** → 协议栈内存池满了，调大
   `BLE_MEMHEAP_SIZE` 或减小 `BLE_BUFF_MAX_LEN`
4. 发送成功后没有等确认就连续发 → 要考虑用 `ATT_HandleValueCfm()` 做流控

### Q9: 想用主机（Central）功能

**CH572 做不到。** 见 [`架构与适配分析.md` 第四节](架构与适配分析.md#四可行性边界明确写下来避免返工)。
需要主动扫描/发起连接请换 **CH592**。

### Q10: 单步调试时发现 `_eusrstack` 附近被改写

栈溢出。减小 `BLE_MEMHEAP_SIZE` 腾出栈空间，或者减少应用的深层调用/大局部变量。

### Q11: ROM 方式下能连上但收不到数据 / BLE 完全不工作

按这个顺序查：

1. **ROM 镜像烧了吗？** ROM 方式必须先把 `lib\CH572BLE_ROM.hex`
   烧到 `0x00020000`。只烧应用固件的话，所有 API 调用都会跳到空白 Flash。
2. **调 `InstallRomIrqHandlers()` 了吗？** 这是 ROM 方式最容易漏的一步。
   BLE 的基带/链路层中断处理在 ROM 里，不注册钩子的话射频中断触发后
   会停在启动文件的弱定义死循环，表现为"能广播但一连接就死"或"完全连不上"。
3. **是不是误链了 `-lCH572BLE`？** 检查一下应用 elf：
   ```powershell
   riscv32-esp-elf-nm build\out\ble_uart-rom.elf | findstr BLE_LibInit
   ```
   有输出说明又链了一份静态库，应该去掉 `-lCH572BLE`。
4. **`Link_rom.ld` 里的 `FLASH_ROM_END` 和实际 ROM 基址对得上吗？**
   对不上会导致应用和 ROM 抢同一段 Flash，ROM 被覆盖。

### Q12: ROM 方式编译报 `implicit declaration of function 'GAPRole_CentralInit'`

这是**预期行为**。CH572 的 ROM 镜像里没有主机角色 API，
所以 `CH572BLE_ROM.h` 刻意不定义这些宏。
如果确实需要主机功能，只能换 CH592。

### Q13: 想改 ROM 占用的地址/大小

两处必须同步改：

1. `scripts\make_rom.ps1 -RomBase 0x0000XXXX`
2. `src\Ld\Link_rom.ld` 里的 `FLASH_ROM_END`（改成 ROM 实际结束位置）

ROM 实际结束位置在构建日志里能看到：

```
ROM 占用 : 0x00020000 - 0x00035CE3  （89,316 字节 / 87.2 KB）
```

把 `FLASH_ROM_END` 设成「ROM 起始地址 − SNV 大小」（当前 ROM 在 0x20000、SNV 4 KB，
所以是 `0x1F000`）。也可以直接跑 `make_rom.ps1 -Probe` 让它自动算出推荐值。

### Q14: ROM 方式比静态库方式还多烧 88 KB，划算吗？

看场景：

- **只有一台设备、不升级** → 静态库方式更省事，一个 hex 搞定。
- **要 OTA 升级** → ROM 方式明显划算：
  - 升级包从 229 KB 降到 19 KB（省 92% 流量与时间）
  - 升级过程不动协议栈，变砖风险低
  - 应用区只有几十 KB，回滚 / 双备份都更容易安排
- **量产烧录** → ROM 一次烧完，之后只刷小固件，产线更快。

### Q15: 脚本报"意外的属性 CmdletBinding"之类奇怪的语法错误

这是 `.ps1` 文件的 **BOM（字节顺序标记）** 问题：

- Windows PowerShell 5.1 读 `.ps1` 时，**没有 BOM 就按系统 ANSI（中文系统是 GBK）解析**。
  本工程脚本里有大量中文注释，按 GBK 解析会直接语法报错。
- 但**多**了一个 BOM（重复的 U+FEFF）同样会报这种莫名其妙的错误。

用编辑器改过脚本之后跑一下：

```powershell
python tools\fix_ps1_encoding.py
```

它会保证每个 `.ps1` 有且仅有一个 UTF-8 BOM，并顺手修正。

### Q16: 构建日志里出现 `no entry in archive` 或"找不到源文件"

这类"工具行为诡异但退出码正常"的问题，几乎都是 **cmd 引号解析**引起的 ——
因为 MounRiver Studio 2 的工具链路径里带空格（`...\RISC-V Embedded GCC12\bin\`）。

本工程已经把调用方式做成"生成临时 `.bat` 再执行"，绕开了这个坑。
如果你自己写脚本调用工具链，注意两点：

1. 不要把参数写成 GCC 的 `@响应文件` —— 它的 `@file` 语法会把 Windows 路径的
   反斜杠当转义符吃掉（`C:\a\b.c` 变成 `C:ab.c`），报"找不到源文件"；
2. 尽量切到目标目录、用相对路径，减少带空格的绝对路径出现。

### Q17: ROM 镜像能和应用合并成一个 hex 吗？

可以。用 `objcopy` 或 hex 合并工具把两个 hex 拼起来即可，注意地址段不重叠。

本工程默认输出两个独立 hex（便于单独升级应用）。
合并属于产线工具链的事，后续可以加一个 `merge_hex.ps1`。
